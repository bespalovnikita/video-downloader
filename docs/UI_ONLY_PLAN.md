# Переход к одной UI-версии Video Downloader

Все семь этапов плана реализованы в коде отдельными изменениями. Исходная точка — main после PR #36 и #37, коммит `5f378b17de14cf199d8aa04314259bc8fbe7d11e`. Этот документ фиксирует получившуюся структуру, границы этапов и проверки перед выпуском. Результаты конкретного прогона подтверждаются Windows CI соответствующего PR; публикация выполняется после зелёного CI и merge в main.

## Полученный результат

Одна Windows-версия на текущем стеке C# / .NET 8 / WPF, один `VideoDownloader.exe`, один пакет выпуска и одна команда сборки. Пользователь запускает EXE напрямую. CMD-запуск, пользовательский консольный загрузчик, резервный PowerShell GUI/движок и EXE-обёртка над PowerShell удалены.

URL, `.txt`, `.url` и `videodownloader://` открывают или пополняют UI. Сохранены доставка аргументов существующему экземпляру, трей и работа при скрытом основном окне. yt-dlp, FFmpeg/ffprobe и плагин `collection-plugins/` остаются фоновыми инструментами. Пользователю не нужны отдельные PowerShell, Python или .NET Runtime. PowerShell используется для сборки/CI, Python — для тестов коллектора.

## Этап 1. Поведение и покрытие

Составлена [матрица пользовательских контрактов](UI_ONLY_COVERAGE.md). Сохраняемые группы:

| Группа | Проверки |
| --- | --- |
| Добавление | URL, TXT, InternetShortcut, буфер, протокол, второй экземпляр, повторный вход во время диалога, точная идентичность URL |
| Названия и превью | Холодный worker/subprocess, все пути добавления до Start без выбора строки, кеш и TTL, URL/название, ошибки изображения и записи кеша |
| Подписки | Baseline/импорт, обязательный полный обход, RSS fallback, новинки, обычная история успехов, уведомление один раз, прогресс и отмена |
| Загрузки | Фактические аргументы yt-dlp, профили, контейнеры, параллельность, live Add, pause/resume, Stop/Retry, transfer totals |
| Файлы и процессы | Staging, no-overwrite, OwnedPaths, NTFS junction, частичная очистка, дерево работников и сохранность независимых процессов |
| Восстановление | Настройки и очередь, прежние JSON/JSONL, Result replay, живой старый worker, повреждённые файлы |
| UI и выпуск | Трей, закрытие/восстановление, русские подписи, зависимости, версия EXE/тега и состав пакета |

Добавлены фиксированные `tests/fixtures/legacy/`: session, subscriptions, history, preview cache, старые Result-события и незавершённая очистка. Их читают production-компоненты C#, без генерации данных второй реализацией. Холодная цепочка названий проверяет настоящий worker и дочерний процесс, а готовый кеш отдельно проверяет отображение.

**Критерий приёмки:** реальные исполняемые сценарии покрывают сохраняемые функции; Linux crossbuild не выдаётся за выполнение WPF/NTFS-тестов.

## Этап 2. Запуск интерфейса

Удалены `NativeCli` и пользовательская ветка `--cli`. Сохранены singleton, named pipe, протокол и импорт URL/TXT/InternetShortcut. `GuiInstanceTests` запускает два настоящих процесса через `Program.RunGui`: второй передаёт полный массив аргументов и выходит, а существующее скрытое окно восстанавливается без потери очереди.

Исторически CMD-launcher и старый упаковщик удалялись вместе на этапе 3, чтобы между этапами CI не ссылался на отсутствующие файлы.

**Критерий приёмки:** EXE запускает UI на чистой Windows без PowerShell и установленного .NET Runtime; повторный запуск, импорт и трей сохраняют поведение.

## Этап 3. Одна реализация и сборка

Удалены CMD-launcher, прежний launcher-проект, PowerShell GUI/движок, runtime-модули, их упаковщик, старый workflow, тесты второй реализации и CLI-руководство. Сохраняемые проверки русских профилей, smoke и версии перенесены в `scripts/` и проверяют единственное приложение. Совместимость подтверждается legacy fixtures.

`scripts/build.ps1 -Task Build|Test|Publish` используется разработчиком и единственным Windows workflow. `Publish` создаёт автономный ZIP и SHA-256; main-only release передаёт выбранную версию через тот же интерфейс. Проверка состава отклоняет CMD, PowerShell runtime/scripts и launcher вместо настоящего приложения, сохраняет XAML, ресурсы, yt-dlp и исходники встроенного коллектора.

**Критерий приёмки:** один workflow и один пользовательский пакет, версия EXE совпадает с тегом, PR не получает права на публикацию. Исторические имена процессов допустимы в совместимом чтении данных и fixtures.

## Этап 4. Владельцы состояния UI

`UI/Views/NativeWindow*` связывает окно, обработчики и сервисы. В `UI/Controllers/` выделены:

- `QueueSessionController`: очередь, результаты, активная сессия, статистика и конечные уведомления;
- `PreviewController`: текущее превью, фоновые названия, известные метаданные и отображение ошибок;
- `SubscriptionController`: источники, входящие, ручные проверки, отмена и сохранение;
- `SubscriptionCheckProgressController`: текущий batch/источник, этап, часы, анимация и терминальный итог;
- `WindowLifecycleController`: видимость окна, трей, восстановление и завершение;
- `InputIngressController`: аргументы, файлы, протокол и буфер обмена.

Компоненты получают явные зависимости и владеют своим состоянием. Новые DI-фреймворки и перепись на MVVM не потребовались. Сценарии адаптированы к новым владельцам состояния в том же этапе.

**Критерий приёмки:** проверки очереди, отмены, закрытия/повторного открытия и поздних callbacks остаются рабочими.

## Этап 5. Движок и данные

В `Downloads/` построение аргументов выделено в `YtDlpArguments`, машинные события и диагностика — в `YtDlpOutputParser`. Windows pause/resume находится в `Infrastructure/Windows/WindowsDownloadPause`. Согласованные завершение, отмена, публикация и cleanup остаются у `DownloadCoordinator`.

В `Persistence/` `AppPersistence` сохраняет очередь/настройки, `SuccessfulDownloadHistory` — историю успехов. `Compatibility/LegacySessionReader` читает прежние Result-события и проверяет живой старый worker. Форматы данных не менялись.

Сохранены `ManagedChildProcess`, индивидуальный staging, no-overwrite и проверки OwnedPaths/reparse. При восстановлении не теряются `PendingRemoval`, `CleanupPaths`, `DeferredToNextStart`, `OutputRoot` и связи подписки. Удаление старого runtime не отменяет чтение его данных.

**Критерий приёмки:** прежние данные читаются без потерь, повреждённые файлы не перезаписываются, отмена затрагивает только собственные файлы и процессы.

## Этап 6. Отдельный WPF test host

`tests/VideoDownloader.UiTests/` ссылается на настоящее приложение через ProjectReference и создаёт его окна/контроллеры. `UiScenario` и вспомогательные сценарии принадлежат тестовой сборке; нужные internal-точки открыты через InternalsVisibleTo. Изолированный профиль защищает пользовательские настройки.

Исторический переключатель `--ui-self-test` удалён из entry point, а тестовые partial-классы исключены из продукта. Unit/integration-тесты движка остаются в отдельном `tests/VideoDownloader.Tests/` и не создают пользовательский консольный режим. Проверка release isolation отклоняет тестовые сборки и сценарии в пакете.

**Критерий приёмки:** пользовательский EXE содержит только приложение, отдельный host выполняет весь набор настоящих WPF-сценариев.

## Этап 7. Итоговая структура

```text
src/VideoDownloader/
  UI/Views/
  UI/Controllers/
  Downloads/
  Subscriptions/
  Preview/
  Persistence/
  Compatibility/
  Infrastructure/Windows/
  VideoDownloader.csproj
tests/
  VideoDownloader.Tests/
  VideoDownloader.UiTests/
  fixtures/
scripts/
collection-plugins/
assets/
.github/workflows/
```

Остался один проект приложения и два тестовых проекта. Пути в project content, workflow, скриптах и документации согласованы; namespace приложения сохранён. XAML в исходниках находится в `UI/Views/`, а внутри пользовательского ZIP — по прежним путям `ui/`. Расположение плагина и `%LOCALAPPDATA%\VideoDownloader` не изменилось.

В README оставлены три команды разработчика:

~~~powershell
pwsh -NoProfile -File scripts/build.ps1 -Task Build
pwsh -NoProfile -File scripts/build.ps1 -Task Test
pwsh -NoProfile -File scripts/build.ps1 -Task Publish
~~~

**Критерий приёмки:** сборка из чистого checkout, реальные Windows unit/integration/WPF/NTFS-тесты, проверка состава ZIP и релиз после зелёного main. Перемещение исходников не меняет пользовательские форматы или поведение.

## Что осталось вне перехода

[BACKLOG.md](../BACKLOG.md) описывает развитие функционала. Автоматические проверки подписок, Планировщик Windows, автоскачивание и новые правила этим переходом не реализованы. Их добавление требует отдельной задачи; текущая версия сохраняет ручную проверку и запуск загрузок через Start.
