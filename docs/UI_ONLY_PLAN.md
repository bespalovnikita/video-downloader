# План перехода к одной UI-версии Video Downloader

Исходный план подготовлен после слияния PR #36 и #37, коммит `5f378b17de14cf199d8aa04314259bc8fbe7d11e`. Этап 1 вошёл в main через PR #38. Дальнейшие этапы выполняются отдельными PR с Windows CI; ниже сохранены их границы и критерии готовности.

## Целевой результат

Одна Windows-версия на текущем стеке C# / .NET 8 / WPF, один `VideoDownloader.exe`, один пакет выпуска и один путь сборки. Пользователь запускает EXE напрямую. CMD-запуск, отдельный режим загрузки из консоли, PowerShell GUI/движок и EXE-обёртка над PowerShell удалены.

Передача URL, списков `.txt`, ярлыков `.url` и `videodownloader://` остаётся способом открыть или пополнить UI. Сохраняются доставка аргументов уже работающему экземпляру, трей и работа при скрытом основном окне.

yt-dlp, FFmpeg/ffprobe и плагин `collection-plugins/` остаются фоновыми инструментами приложения. Для запуска UI не нужны отдельные PowerShell 7, Python или установленный .NET Runtime. PowerShell для сборки/CI и Python для тестов коллектора разрешены как инструменты разработчика; они не входят в пользовательский пакет.

Нативный стабильный ZIP уже не включает CMD и PowerShell runtime. Основное дублирование сейчас находится в исходниках, старом упаковщике и втором workflow.

## Порядок реализации

Каждый этап — отдельный PR с проверками и актуализацией затронутой документации. Переход к следующему этапу — после выполнения критерия готовности предыдущего. Перенос каталогов и изменение поведения не смешиваются в одном PR.

### Этап 1. Зафиксировать поведение и перенести необходимое покрытие

Составить матрицу «пользовательский сценарий → проверка единственной C#-реализации». Сохранить основные группы:

| Группа | Проверки |
| --- | --- |
| Добавление материалов | URL, `.txt`, `.url`, буфер, протокол, повторный вход во время диалога, неизменность точного URL |
| Названия и превью | Холодное получение метаданных через worker, попадание в кеш, названия всех путей добавления до Start, выбор URL/названия, ошибки изображения и записи кеша |
| Подписки | Первый baseline/импорт, повторный полный обход, RSS fallback, новинки, история обычных URL, повторная постановка, прогресс и отмена |
| Загрузки | Профили, контейнер, параллельность, live Add, pause/resume, Stop/Retry, transfer totals |
| Файлы и процессы | Staging, no-overwrite, принадлежность путей, junction/reparse, отмена и частичная очистка, дерево дочерних процессов |
| Восстановление | Настройки и очередь, прежние форматы JSON, старые Result-события, живой старый worker, повреждённые файлы |
| UI и выпуск | Трей, закрытие/повторное открытие, русские подписи, зависимости, версия EXE/тега, состав пакета |

Сценарии, проверяемые только через PowerShell, перенести до удаления runtime. Конкретный пример: `tests/title-ingress-tests.ps1` проверяет холодную цепочку метаданных; нативная WPF-проверка добавления URL/файлов сейчас использует готовый кеш. Добавить соответствующую холодную проверку C#.

Вместо зависимости от второй реализации подготовить фиксированные legacy-данные в `tests/fixtures/`: session, subscriptions, history, cache, Result-события и незавершённая очистка. Не заменять проверки простым поиском строк в исходниках.

**Готовность:** все сохраняемые сценарии проверяются на C#; в матрице нет потерянного покрытия. Старую реализацию ещё можно использовать для сверки на этом этапе.

### Этап 2. Упростить нативный запуск

Удалить ветку `--cli` и класс `NativeCli` из `native/Program.cs`. Оставить запуск нативного WPF EXE, singleton и named pipe. Перевести пользовательские инструкции для нативного пакета на прямой запуск EXE.

`start-gui.cmd` и `launcher/` пока сохранить: старый `build-exe.ps1` ещё проверяет и упаковывает их, а второй workflow вызывает этот скрипт. Их удаление выполняется атомарно на этапе 3 вместе с прежним упаковщиком и workflow.

Сохранить пользовательские входы URL / TXT / InternetShortcut / `videodownloader://`: они передают данные в UI и не запускают headless-загрузку. Проверить регистрацию протокола на прямой вызов EXE. `--ui-self-test` пока остаётся исключительно для существующего CI и удаляется на этапе 6.

Нативные unit/integration-тесты уже вызывают `DownloadCoordinator` напрямую и используют собственный тестовый EXE как fixture yt-dlp; удаление пользовательского `--cli` не должно их отключать.

**Готовность:** чистая Windows без PowerShell 7 и установленного .NET Runtime запускает UI напрямую. Импорт, протокол, второй экземпляр и трей работают без пользовательского консольного окна.

### Этап 3. Удалить вторую реализацию и оставить одну сборку

После переноса покрытия удалить:

- `start-gui.cmd`;
- проект `launcher/`;
- `ytdl-manager-gui.ps1`;
- `ytdl-manager-v8.ps1`;
- runtime-модули `lib/`;
- старый `build-exe.ps1`;
- `.github/workflows/build-windows.yml`.

Все нужные проверки перед удалением должны присутствовать в едином native workflow. Сохранённые скрипты запуска тестов/сборки расположить в `scripts/`, сделать единую команду native build/publish и использовать её из CI. Изменения зависимых тестов, CI и удаляемых файлов выполнить одним согласованным PR, чтобы main не ссылался на уже удалённый код.

Переписать smoke и проверки русских профилей: сейчас часть из них читает PowerShell GUI и импортирует PS-модуль профилей. Cross-runtime проверки заменить проверками совместимости с legacy fixtures из этапа 1. Сохранить release-version tests, main-only публикацию, SHA-256 и совпадение версии EXE/тега.

В проверке пакета явно отклонять `.cmd`, пользовательские `.ps1/.psm1`, `pwsh.exe` и launcher вместо настоящего UI. Сохранять ресурсы, XAML, yt-dlp и исходники встроенного коллектора.

**Готовность:** один workflow и один пользовательский ZIP. Нет runtime/build-зависимостей от удалённой реализации. Упоминания прежних имён процессов и путей допустимы в legacy fixtures и совместимом чтении данных. Функции UI покрыты сохранёнными проверками.

### Этап 4. Разделить обязанности UI

Сократить общий `NativeWindow`, выделив владельцев конкретного состояния:

- управление очередью и активной сессией;
- предпросмотр и обновление названий;
- подписки: проверка, очередь источников, входящие и уведомления;
- отображение прогресса подписок и его жизненный цикл;
- трей и управление видимостью окна;
- получение аргументов/импорт/протокол.

`NativeWindow` остаётся тонким местом связывания окна, обработчиков и сервисов. Например, контроллер подписок владеет своей проверкой, отменой, таймером и текущим batch; эти поля не распределяются между unrelated partial-файлами.

Начать с `NativeWindow.Subscriptions.cs` и `NativeWindow.cs`, поскольку в них смешаны UI, orchestration, сохранение и жизненный цикл. Просто разнести строки по partial-файлам недостаточно: нужны понятные владельцы состояния и явные зависимости через конструкторы. Новые DI-фреймворки и полная перепись на MVVM на этом этапе не требуются.

При переносе private-полей сразу адаптировать обращающиеся к ним self-test сценарии в том же PR: они должны работать с новым владельцем состояния и продолжать компилироваться. Этап 6 затем меняет место запуска этих уже адаптированных сценариев, а не откладывает их исправление.

**Готовность:** изменение подписок или превью затрагивает свой контроллер, а не несколько частей общего окна; тесты отмены, закрытия, повторного открытия и поздних callbacks остаются зелёными.

### Этап 5. Упростить движок и хранение данных

Из `DownloadCoordinator.cs` выделить построение аргументов yt-dlp, разбор машинных событий и Windows pause/resume. Сохранить единый согласованный механизм завершения попытки, отмены, публикации и cleanup; не дробить его так, чтобы появились новые гонки.

Разделить ответственность `Persistence.cs`: очередь/настройки, история успехов и совместимость старых сессий. Legacy-чтение Result-событий и проверку живого старого работника оставить отдельным компонентом `Compatibility/LegacySessionReader`.

Сохранить `ManagedChildProcess`, staging каждого задания, no-overwrite и проверки `OwnedPaths`/reparse. Удаление PowerShell-кода не является основанием перестать читать старые пользовательские данные или сбрасывать `PendingRemoval`, `CleanupPaths`, `DeferredToNextStart`, `OutputRoot` и связи подписок.

Сами форматы `session.json`, `subscriptions.json` и истории на этапе структурного рефакторинга не менять. Если отдельная миграция понадобится позднее, выполнять её самостоятельным изменением с тестами и защитой исходных данных.

**Готовность:** старые данные восстанавливаются без потерь, повреждённые файлы не перезаписываются; отмена удаляет только принадлежащие заданию файлы, чужие пути и независимые процессы сохраняются.

### Этап 6. Вынести UI-тесты из релизного EXE

Создать отдельный WPF test host для настоящих окон и контролов. Перенести сценарии из `NativeUiSelfTest`, `QueueUiSelfTest`, `SubscriptionUiSelfTest` и title self-test в тестовый проект.

Текущие тестовые partial-классы имеют доступ к private-полям приложения, поэтому их нельзя просто переместить в другую сборку. После этапа 4 проверять окно через реальные контролы, контроллеры и выделенное состояние; необходимые internal-точки открыть только тестовой сборке через `InternalsVisibleTo`. Сохранить изолированный профиль и отсутствие обращения к пользовательским настройкам.

После перехода CI на отдельный host удалить `--ui-self-test` из пользовательского entry point и исключить сценарии тестов из релизной сборки. Headless-тесты движка остаются тестами и не создают новую консольную версию продукта.

**Готовность:** release EXE содержит только приложение; отдельный test host проходит все реальные UI-сценарии и проверки завершения процессов.

### Этап 7. Упорядочить каталоги и завершить документацию

Переносить пути последним отдельным PR, когда обязанности и сборка стабилизированы. Компактная целевая структура:

```text
src/VideoDownloader/
  UI/Views/
  UI/Controllers/
  Downloads/
  Subscriptions/
  Preview/
  Persistence/
  Compatibility/
  Infrastructure/Windows/
  VideoDownloader.csproj
tests/
  VideoDownloader.Tests/
  VideoDownloader.UiTests/
  fixtures/
scripts/
collection-plugins/
assets/
.github/workflows/
```

Это один проект приложения и два тестовых проекта; отдельная сборка на каждый каталог не нужна. Согласованно обновить project content, пути XAML/ресурсов, plugin discovery, workflow и скрипты. Для пользователя сохранить понятный состав ZIP и прежнее расположение настроек.

Актуализировать README, GUI, AGENTS, NATIVE_MIGRATION, RELEASING и BACKLOG. Старое CLI-руководство убрать из актуальной документации. В quick start оставить запуск EXE; для разработчика — одну команду build/test/publish.

**Готовность:** проект собирается из чистого checkout, устанавливаемых пользователю компонентов не прибавилось, все функции UI и совместимость данных проверены, единственный стабильный пакет опубликован из зелёного main.

## Порядок начала

Первый рабочий PR — матрица покрытия, legacy fixtures и закрытие конкретных пробелов native-тестов. После него можно снимать лишние точки запуска. Удаление старой реализации, изменение форматов данных и массовое перемещение файлов в одном PR не совмещать.

Проверки первого этапа перечислены в [матрице покрытия](UI_ONLY_COVERAGE.md).
Состав текущего релиза и инструкции запуска остаются в README и GUI;
этот документ описывает последовательность изменений, а не уже удалённые компоненты.
