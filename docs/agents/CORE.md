# Общие правила для агента

Прочитай этот документ и [SHARED.md](SHARED.md) перед изменениями. Затем выбери платформенный контракт по [корневому AGENTS.md](../../AGENTS.md). Пути в кодовых фрагментах указаны от корня репозитория.

## Цель и границы

Video Downloader имеет две пользовательские UI-версии: Windows на C# / .NET 8 / WPF и Android на Kotlin / Jetpack Compose. Пользовательского CLI, CMD-launcher и резервного GUI нет. PowerShell и Python могут быть инструментами разработки, но не требованием к пользователю Windows-приложения.

Разделяй платформенные проекты, runtime и локальные форматы данных. Не переноси код Android в C#-проект и не приписывай одной платформе поведение другой. Сохраняй совместимость уже существующих пользовательских данных; импорт не доказывает владение файлами.

## Общие инварианты

- Идентичность URL — точное ordinal-сравнение с учётом регистра. Идентичность материала подписки — `SubscriptionId` + точный URL. Не объединяй существующие адреса по media ID и не нормализуй произвольно query. Допустимые правила формирования новых адресов адаптерами описаны в платформенных контрактах.
- Обнаружение, baseline, Skip, добавление в очередь и код завершения yt-dlp сами по себе не являются успехом. История и обработанное состояние требуют проверенного медиа и успешной публикации. Отмена и ошибка туда не записываются.
- Не перезаписывай и не удаляй чужие файлы. Публикация и очистка опираются на собственный staging и подтверждённое владение, а не только на путь из снимка или импортированного файла. Согласуй отмену, публикацию и запись истории у владельца загрузки.
- Подписки проверяются вручную. Проверка, импорт, восстановление и постановка в очередь не запускают скачивание; граница запуска — явный Start. Планировщик и автоматические проверки требуют отдельной задачи.
- Превью не зависят от запуска скачивания или выбора строки. Сеть и тяжёлая работа выполняются вне UI thread, листание готовых изображений не создаёт сеть. Платформенные ограничения кеша, числа изображений и runtime различаются.
- Повреждённые пользовательские данные не перезаписывай автоматически. Не включай секреты, cookies, локальные SDK/кеши и build artifacts в Git. Логируй полезную диагностику с маскированием секретов; отказ необязательной диагностики не меняет результат скачивания.
- Документация описывает текущую реализацию и ограничения. Идеи и неподтверждённые возможности помещай в [планы проекта](../project/ROADMAP.md). Политика документации — [DOCUMENTATION.md](DOCUMENTATION.md).

## Проверки по области изменения

| Область | Обязательная проверка |
| --- | --- |
| Windows-код, WPF, Windows-тесты, скрипты и сборка | `pwsh -NoProfile -File scripts/build.ps1 -Task Test`; зелёный `native-windows.yml` до merge |
| Состав Windows ZIP | Дополнительно `pwsh -NoProfile -File scripts/build.ps1 -Task Publish` |
| Android-код, runtime, сервис, сборка | Команды и реальные device-сценарии из [ANDROID.md](ANDROID.md); зелёный `android.yml` |
| `collection-plugins/` или общий формат/фикстуры очереди | Проверки обеих платформ; контракт обмена — [SHARED.md](SHARED.md) |
| Только Markdown | Проверка локальных ссылок, якорей, Mermaid и соответствия исходникам; C#-тесты для чистой документации не требуются |

Не подменяй поведенческие сценарии поиском маркеров в исходниках или холодную загрузку готовым кешем. Не выдавай офлайн-фикстуру за доступ к живому сайту. Подробности: [Windows](WINDOWS.md#тесты-перед-prmerge), [Android](ANDROID.md), [руководство по тестированию](../developer/testing.md).

PR только с Markdown может не запускать workflows из-за фильтров путей. После push в `main` полный Windows workflow запускается независимо от состава изменений.

## Автоматические стабильные GitHub Releases

Любой коммит в `main` после успешного native Windows CI публикуется как стабильный GitHub Release. Main-only job `release` в `.github/workflows/native-windows.yml` создаёт следующий тег `v2.0.N`, Windows ZIP, SHA-256 и Release Notes. Публикация из PR запрещена: по умолчанию `contents: read`, запись только в release job для `main`.

- Нумерацией управляет `.github/scripts/ReleaseVersion.psm1`; `scripts/release-version-tests.ps1` выполняется в составе общей команды Test.
- Версия публикуемого EXE совпадает с Git-тегом; параметры publish переопределяют версию проекта.
- Release не публикуется при провале native unit/integration/UI/security tests.
- Не изменяй и не удаляй ранее опубликованные или чужие релизы. Существующий draft `v1.0.0` не трогай.
- `main` означает релизную готовность: до merge проверь API и интерфейсную совместимость. Учитывай, что это относится и к Markdown-коммитам.
- Android debug APK — отдельный CI-артефакт. Публичная подпись и выпуск APK требуют отдельной настройки; не подключай debug APK к автоматическому Windows Release.
- Сохраняй лицензионные ограничения зависимостей и [Android notices](../../android/THIRD_PARTY_NOTICES.md). Лицензию собственного кода не меняй без отдельного решения владельца.

Порядок выпуска и проверки результата: [руководство разработчика](../developer/releases.md).

## Рабочий процесс

Для нетривиальных изменений:

1. Создай ветку от актуального `main`.
2. Делай небольшие осмысленные коммиты.
3. Открой PR с описанием поведения и применимой валидации.
4. Выполни проверки по области изменения; дождись CI, если он запускается.
5. Мержи после успешных проверок в пределах действующего поручения пользователя.

Не коммить `dist` и другие build artifacts, если задача явно этого не требует. Эти инструкции не вводят отдельного согласования обычных исправлений, создания PR или merge: учитывай полномочия, уже предоставленные пользователем в текущей работе.
