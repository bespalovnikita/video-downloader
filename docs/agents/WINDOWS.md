# Контракты Windows для агента

Прочитай после [CORE.md](CORE.md) и [SHARED.md](SHARED.md), если задача затрагивает C#, WPF, Windows-данные, зависимости, сборку или тесты. Пути в кодовых фрагментах указаны от корня репозитория. Это действующие ограничения реализации, а не список будущих функций.

## Проект и точки входа

- Точка запуска — `VideoDownloader.exe`; пользовательского CLI, CMD-launcher и резервного GUI нет.
- Единственный Windows-проект приложения: `src/VideoDownloader/VideoDownloader.csproj`. Окна и XAML находятся в `src/VideoDownloader/UI/Views/`, владельцы состояния — в `src/VideoDownloader/UI/Controllers/`.
- Модели и entry point находятся в корне проекта; загрузки, превью, подписки, хранение и совместимость разделены по `Downloads/`, `Preview/`, `Subscriptions/`, `Persistence/`, `Compatibility/`; Windows-процессы — в `Infrastructure/Windows/`.
- C# unit/integration-тесты: `tests/VideoDownloader.Tests/`; настоящие WPF-сценарии: `tests/VideoDownloader.UiTests/`. Оба проекта ссылаются на приложение через ProjectReference. Не включай тестовые partial-классы, сценарии или переключатели запуска тестов в релизный EXE.
- Единые команды build/test/publish: `scripts/build.ps1`. PowerShell нужен разработке и CI, не приложению.
- Релизный ZIP автономен: пользователь не устанавливает PowerShell, Python или .NET Runtime.
- Сохраняй чтение прежних пользовательских данных в `%LOCALAPPDATA%\VideoDownloader`, включая финальные Result-события и защиту от живого старого работника `pwsh`.

## Архитектура и владение процессами

WPF-интерфейс и движок расположены в `src/VideoDownloader/`, два тестовых проекта — в `tests/`. Релизный ZIP создаётся workflow `native-windows.yml`.
Пользовательская сборка не должна включать CMD/PowerShell-скрипты или запускать `pwsh.exe`. URL, TXT, InternetShortcut и `videodownloader://` передаются в интерфейс; второй экземпляр использует singleton и named pipe и возвращает существующее окно из трея.

При изменениях в `src/VideoDownloader/`:
- Запускай native Windows CI: сборка, открытие окна WPF, реальные Add/Remove,
  clipboard-preview, .url import и checkpoint через изолированный UI-тест.
- Запускай офлайн тесты реального `yt-dlp.exe`: параллельная загрузка,
  queued/running cancellation, late live Add, pause/resume.
- При отмене URL используй tombstone и синхронизацию конечного результата:
  публикация и удаление файлов должны быть согласованы, без оставшихся media.
- `DownloadItem` сохраняет прежние `PendingRemoval`, `CleanupError`,
  `CleanupPaths`, `StageDir`, `RunDir`, `AttemptFinished`, `DeferredToNextStart`.
  Не удаляй активную строку до подтверждения работника. Ошибка очистки и
  частичный манифест переживают checkpoint, Clear Queue и обновление приложения;
  Start/Retry исключают такие строки. Полный список опубликованных файлов
  сохраняется даже при неудачном rollback; меняй списки атомарной заменой,
  чтобы сериализация GUI не гонялась с изменением коллекции работником.
- Старый Result не применяется к `DeferredToNextStart`. Сохраняй контекст
  очистки и исходный `OutputRoot` также при чтении legacy Result-событий.
- Успех требует валидного `after_move:__VD_FILE__` media path из staging;
  код 0 без медиа не должен публиковать sidecars или пополнять историю.
- Счётчики transfer учитывают сброс при retry; постоянная HTTP/auth ошибка
  имеет приоритет над transient-подсказками в том же diagnostic.
- Операции удаления разрешены только с известным `OwnedPaths`; неизвестный
  путь из старого checkpoint сам по себе **не является доказательством владения**.
- Относись к C# `session.json`, `successful-downloads.jsonl`, preview cache
  как к совместимым с ранее использованными форматами.
- Из старого `Engine.EventsPath` читай финальные Result-события: старый GUI
  мог умереть до сохранения checkpoint. Активный legacy `pwsh` блокирует
  восстановление и новые native sessions.
- При `Archive` фиксируй каталог назначения на всю сессию; ночной переход
  даты не должен менять место публикации и удаления.
- Создавай native процессы загрузки, превью и сканирования yt-dlp через `ManagedChildProcess`: индивидуальный job назначается атомарно через `PROC_THREAD_ATTRIBUTE_JOB_LIST`; наследуются только явные pipe handles. Не помещай GUI или открываемые пользователем приложения в job работника. `yt-dlp -U` запускается отдельно: его штатная отложенная очистка `.old` должна пережить выход обновляющего процесса. Проверяй аварийный выход владельца, потомков, независимый процесс, аргументы, окружение и оба pipe в Windows CI.
- До запуска загрузок UI проверяет FFmpeg/ffprobe. Выбранный контейнер требует и merge, и remux; native-публикация проверяет расширение результата.
- После модального подтверждения live Add повторно проверяй наличие URL и идентичность активной сессии. Повторный вход не создаёт дубликат; завершённая или заменённая сессия оставляет ссылку для следующего Start. Проверяй это реальными вложенными WPF-диалогами.
- Границы вывода поддерживают корень диска/UNC с одним завершающим separator; сам root не считается дочерним файлом.
- Разрешённая повторная загрузка выбирает свободный суффикс для всего batch media/sidecars. `OwnedPaths` содержит только новые файлы. Helper без явного `renameCollisions` продолжает отклонять существующий destination; никакой overwrite. Планирование и публикация параллельных заданий согласованы; гонка с внешним процессом не разрешает перезапись чужого файла.
- Не запускай таймеры до восстановления. `SaveCheckpoint` блокируется на всём протяжении диалогов восстановления; ошибка чтения переводит checkpoint в read-only до показа предупреждения. Настройки восстанавливаются при пустой/завершённой очереди и при отказе от восстановления строк. Установка FFmpeg имеет общий шестиминутный deadline скачивания, включая тело при `ResponseHeadersRead`; timeout/cancel удаляет scratch и освобождает кнопки зависимостей.
- Для полной защиты от намеренной TOCTOU-подмены каталогов понадобится
  handle-based Win32 реализация; текущая проверка reparse/junction не даёт
  такой абсолютной гарантии.

Схемы взаимодействия компонентов и совместимость данных описаны в
[архитектуре](../developer/architecture.md), правила выпуска — в
[правилах выпуска](../developer/releases.md).

## Русификация интерфейса и документации

- Пользовательские ошибки локализует `Infrastructure/ErrorMessages.cs` по `CultureInfo.CurrentUICulture` (все локали `ru`); `CurrentCulture` отвечает за числа/даты, не язык сообщений. Перевод применяется только при отображении. Не меняй `RawError`, `CleanupError`, `LastError`, `LastWarning`, текст диагностических файлов/кеша или машинные `State`/`Status`; display-only поля помечай `JsonIgnore`. Сохраняй доступ к исходной диагностике. Для новых правил проверяй русскую и нерусскую UI-локаль, приоритет HTTP/auth над временными ошибками и отсутствие ложных совпадений по ID/URL. Не используй переведённый текст для retry, успеха или восстановления кеша.
- Названия встроенных профилей **локализуются только для отображения**. Идентификаторы `Universal`, `4K archive`, `MP4 compatibility`, `Music MP3`, `Subtitles archive` в `session.json` неизменны.
- Маппинг находится в `src/VideoDownloader/Downloads/ProfileCatalog.cs`.
- WPF-разметка должна содержать две кнопки: `OpenOutputDirectoryButton` возле `RetryFailedButton` и `OpenAppSettingsButton` возле `RegisterProtocolButton`. Обработчики обязательны в UI.
- Для настроек используется **`%LOCALAPPDATA%\VideoDownloader`**, не `%APPDATA%` (Roaming). В C# путь нужно получать из фактического экземпляра `AppPersistence`, чтобы поддерживался тестовый профиль.
- Папка загрузок берётся из UI, а во время активной C#-сессии — из зафиксированного `DownloadOptions.OutputDirectory`; архивирование добавляет подкаталог даты.
- Перед merge обязательно проверь `scripts/russian-ui-tests.ps1` и настоящие WPF-тесты в Windows CI. Единая команда — `pwsh -NoProfile -File scripts/build.ps1 -Task Test`.

## Архитектурные инварианты

### Структурированный прогресс

Не возвращай парсинг обычных строк <code>[download] ...</code> как основной механизм прогресса.

Engine использует:

- <code>--progress-template</code> с <code>__VD_PROGRESS__</code>;
- <code>--print before_dl:__VD_TITLE__:</code>;
- <code>--print before_dl:__VD_PLAN__:</code> с ограниченными полями идентичности материала, форматов и позиции/размера плейлиста;
- <code>--print after_move:__VD_FILE__:</code>.

Структурированный вывод разбирается в `src/VideoDownloader/Downloads/YtDlpOutputParser.cs`, аргументы строит `YtDlpArguments` в том же каталоге. Согласованное завершение, отмена, публикация и очистка остаются в `DownloadCoordinator`.

Human-readable stdout допустимо анализировать только для вспомогательных событий вроде merge/error diagnostics.

`--progress` обязателен вместе с `--print`. Stdout/stderr читаются параллельно. UI показывает progress/скорость/объём/ETA в обеих таблицах. Result не должен повторно прибавлять размер файла к уже учтённому session transfer volume. При чтении старых JSONL-событий не принимай неполный или некорректный Result за терминальный результат; процент прогресса сам по себе не доказывает успех.

### Журнал и трассировка

- Профиль `DownloadOptions.LogProfile` хранится отдельным стабильным ID: `Errors`, `Standard`, `Progress`, `Detailed`. Старые настройки без поля и неизвестный ID используют `Standard`. Выбор профиля скачивания не сбрасывает профиль журнала; изменение подробности действует во время сессии без её перезапуска.
- Передавай снимки диагностических событий со стабильными session/job/worker и попыткой, качеством, компонентом, источником stdout/stderr, порядком и временем. Короткий job вычисляется из точной строки URL; не нормализуй адрес ради логирования. Общую статистику связывай с сессией и составом учитываемых строк.
- Все per-job события, включая `Verbose/yt-dlp` и `Progress/download`, содержат `video_seq` из текущего `DownloadItem.Order` и `video` с названием либо точным URL при неизвестном названии. При Order=0 показывай `video_seq=?`. Метку маскируй до JSON-цитирования и ограничивай 160 символами; в `overall.members` используй те же поля с меткой до 64 символов. Сохраняй job/session/worker и engine `seq`: номер строки не является устойчивой идентичностью. Общий список ограничен 32 строками и 2800 символами, содержит `members_shown` / `members_truncated`; суммарные счётчики учитывают всю сессию.
- Читаемый префикс журнала — `[yyyy-MM-dd HH:mm:ss.fff]` по локальному времени, без зоны и отображаемого `#`-счётчика. Внутренний `Entry.Sequence` и курсор выдачи сохраняются для порядка/вытеснения; это не номер видео и не код цвета. Не обещай цвет по текстовому префиксу: текущий журнал — обычный TextBox. Отдельные `seq`, `ui_seq` и elapsed-поля трассы остаются.
- Прогресс берётся из `__VD_PROGRESS__`, план компонентов — из `__VD_PLAN__`. Общая шкала задачи усредняет выбранные компоненты с равным весом и потолком 99%; этап и сырой процент текущего компонента отображаются отдельно. Только успешная публикация устанавливает 100%. При неизвестном плане/размере коллекции сохраняй честный fallback текущего материала и объясняй ограничение. Смена компонента, сброс байтов и уменьшение процента должны быть объяснимы по трассе. Не маскируй реальные повторы искусственным монотонным `Math.Max`; `N/A`, NaN и Infinity не должны заменять последнее известное значение нулём или попадать в WPF как нечисловой процент. Повтор/quality fallback отмечай отдельной попыткой и состоянием; после начала postprocessing не перезапускай весь download автоматически.
- Ограничивай частоту обычных образцов, размер строк, память, очередь записи и файлы. Записывай файлы в фоне; WPF получает пакеты событий вместо отдельного Dispatcher-вызова на каждую строку. Ошибки sink, записи и ротации не меняют скачивание, историю и публикацию. Переполнение и отказ записи сообщаются в ограниченном виде.
- До сохранения и копирования маскируй URL userinfo/fragment, значения query за пределами разрешённого списка публичных идентификаторов и навигации, известные заголовки и параметры авторизации. Сохраняй диагностически полезные `v`, `list`, `viewkey` и другие ключи из `JournalSanitizer` с точным написанием URL; неизвестные параметры и токены не раскрывай. Не записывай содержимое cookies, полный argv или окружение. Подробный профиль сохраняет stdout/stderr, не требует `--verbose`.
- Сообщения журнала показывай с настоящими переносами строк, включая разделение перевода и исходной диагностики. Продолжения одной записи отделяй от нового заголовка отступом; correlation fields оставляй однострочными. Экран, Copy, Save и текстовые `journal*.log` должны согласованно сохранять многострочный текст. Не делай blanket-unescape произвольных `\\r`/`\\n`: это может повредить Windows-пути. Машинное JSONL-экранирование не меняй.
- Проверяй профили, фильтрацию, маскирование, конкуренцию и ограничения нативными тестами; реальный WPF-сценарий должен проверять переключение, восстановление и копирование. Интеграция с упакованным yt-dlp должна подтвердить независимые трассы четырёх параллельных заданий. Пользовательское описание — [руководстве по журналу](../user/windows-logging.md).

### Предварительная загрузка превью

URL должен попадать в preview-prefetch queue сразу после добавления в Queue. Это немедленная постановка запроса: единственный работник может ждать предыдущий запрос и ответ сайта. Не обещай мгновенную готовность изображения; публикуй название и первую картинку по готовности, не ожидая всей галереи.

Контракт:

- один независимый background preview worker;
- Clipboard URLs во время загрузки получают приоритет в очереди prefetch, а ручной Paste сразу показывает выбранную ссылку в preview панели; Watch clipboard не крадёт текущее выделение;
- metadata + thumbnail запрашиваются заранее;
- клик по строке читает cache;
- если preview ещё не готов, клик только повышает приоритет URL;
- клик не создаёт второй тяжёлый metadata request;
- persistent cache: <code>%LOCALAPPDATA%\VideoDownloader\preview-cache</code>;
- TTL пригодных данных и ответа без кандидатов изображений: **72 часа**;
- cache key: SHA-256 URL.

Получение и кеширование реализованы в `src/VideoDownloader/Preview/PreviewService.cs`.

У правой панели подписок свой выбранный URL: `SubscriptionPreviewController` получает данные и ошибки того же `PreviewController` / `PreviewService`, а не создаёт второго работника. Один выбранный материал показывает известные название, URL, состояние, подписку и время обнаружения сразу, метаданные и до двух пригодных изображений — по готовности. Выбор нескольких строк или отсутствие выбора очищает панель; выбор во входящих не меняет Preview основного окна. Дисковый кеш не читай из UI: используй memory-only `GetCached` и обычный запрос общего работника. Ошибка или поздний callback другой ссылки не стирает сведения текущего материала; пригодные картинки сохраняются при сбое обновления. Закрытие и Dispose отписывают панель от событий и освобождают изображения. Проверяй холодные HTTP-картинки, две разные картинки, быстрый A → B, готовый кеш без сети, множественный выбор, закрытие и повторное открытие.

Пустой результат версии получения 3 с непустым `ThumbnailError` от сети, таймаута или повреждённой картинки повторно проверяется при следующем Request после минуты от `SavedAtUtc`. Автоматического таймера нет; свежую ошибку не повторяй при каждом обращении. Существующее правило отсутствующего FFmpeg отдельно разрешает обновление после его установки. Проверяй обе границы кеша: холодное чтение с диска и прогретый Request.

Явный приём материалов подписки должен вызывать RequestRowPreview для всех принятых пригодных незавершённых строк, включая уже существующие после неудачного полного metadata request. Не меняй принадлежность или состояние существующей строки и не создавай второй worker. Cold ingress-тесты URL/подписки должны подтвердить не только Title, но и реальную HTTP-картинку в кеше до Start и выбора строки основного окна; готовое превью показывается без нового процесса или HTTP-запроса.

После успешного scan ставь в общий preview worker фоновую догрузку обложек материалов всех состояний, включая Baseline/Processed/AlreadyProcessed/Skipped. Для Full используй только подтверждённые `scan.Items`, для RecentWindow — накопленный snapshot источника после ApplyScan. Прежнее исключение исходного набора и обработанных материалов из такой предзагрузки больше не действует. Не начинай backfill после неполного/отменённого/пропущенного из-за паузы scan. Постановка выполняется в фоне и не задерживает scan/общий диалог приёма, не меняет состояний и не запускает скачивание. Актуальные готовые данные не требуют HTTP; сохраняй TTL 72 часа для пригодного/без кандидатов ответа и минутный cooldown пустой ошибки. Проверяй оба scope, все состояния, отсутствие повторной сети и отказ изображений без влияния на scan/очередь.

Ошибки превью должны давать полезную ограниченную диагностику: video URL, image URL и номер кандидата при наличии, этап, HTTP-статус и размеры при наличии ответа, тип/причину исключения и вложенной причины. Метаданные и запись кеша тоже сообщают точный URL и этап. Маскируй секреты до записи; не сохраняй cookies, HTML и произвольные ответы сайта. Ошибка диагностического обработчика не должна останавливать preview worker.

Общий deadline запроса — 30 секунд, включая дочерний процесс,
заголовки и изображения. Для всей галереи дополнительно действуют общие 12 секунд,
2 МБ на изображение и 12 МБ на набор. Максимум 15 изображений из 60 кандидатов;
совпадающие байты не дублируй. Таймаут метаданных завершает дочерний процесс и освобождает
единственного работника; ошибка изображения сохраняет текстовые метаданные.
Используй отдельный token для всего чтения тела при ResponseHeadersRead.

PreviewData сохраняет прежний positional ctor и `ThumbnailBase64` первой картинки; новый `ThumbnailsBase64` добавлен совместимо. Кеш версии 1 с PreviewFetchVersion<3 можно показывать сразу и дополнять без дублирования процесса. Полный `Get` с дисковой проверкой галереи не вызывай из UI; для него нужен быстрый memory-only `Peek`, а чтение/проверка диска выполняется работником. Прогрессивные callbacks не должны перезаписывать неизменившиеся названия и сериализовать checkpoint при каждой картинке. При неудачном обновлении пригодная прежняя обложка остаётся видимой. Автолистание работает только при наведении на видимую галерею; уход мыши, смена URL, скрытие и Dispose останавливают таймер. Проверяй реальные mouse enter/leave/wheel, сохранение выбранного кадра при прогрессивных обновлениях и отсутствие сети от листания.

Кеш строк в памяти ограничен 64 МиБ и 128 записями; дисковый кеш имеет мягкий предел 512 МиБ. Автоочистка касается только собственных SHA-256.json в preview-cache, не следует reparse points и выполняется вне UI. Ошибка кеша не блокирует метаданные.

Название из SubscriptionItem переносится в main queue до preview; при восстановлении очереди пустые/URL-placeholder названия дополняются одним bulk-чтением подписок по точным SubscriptionId+Url. Ошибка необязательного файла подписок не блокирует восстановление обычной очереди. Preview с пустым заголовком не стирает известное название. Не определяй пригодность миниатюры только по суффиксу URL; проверяй байты, ограничивай весь набор кандидатов одним бюджетом и используй существующий FFmpeg для WebP/AVIF. Конвертер читает только собственный локальный scratch, ограничивает память/выход и отменяется вместе с запросом. Старая точная ошибка фильтра JPEG/PNG не должна удерживать пустую обложку в кеше 72 часа.

До принятия обложки проверяй реальное декодирование кадра, а не только сигнатуру; некорректный кандидат не блокирует запасной. Исходный кадр ограничен 16 777 216 пикселями, декодируемый растр — 720 по большей стороне без увеличения. Проверяй изображения при чтении дискового кеша; проверенную память не декодируй повторно при каждой постановке URL. Кеш использует точное ordinal-сравнение URL, включая проверку identity памяти. Ошибка записи кеша не должна отбрасывать полученные данные из памяти и панели. Полный сбой метаданных сообщает URL и причину интерфейсу, завершает состояние загрузки, сохраняет известное название и не меняет превью другой ссылки. Сам перенос известного названия из подписки сразу обновляет заголовок текущего совпадающего превью без сети; отдельный RequestRowPreview при явном приёме строки использует обычные правила кеша и повтора.

Профили задают полный набор параметров: качество,
кодек, контейнер, AudioOnly, Archive, субтитры и встраивание данных. Только
«Архив 4K» включает Archive; остальные профили сбрасывают его. Пути, cookies,
скорость и число работников не меняются при выборе профиля.

### Очередь во время активной загрузки

Во время активной загрузки пользователь должен иметь возможность:

- выбирать строки;
- смотреть preview;
- open/copy URL.

Во время активной сессии **Remove разрешён**: пользователь может убрать URL из очереди, а для уже начатого/законченного задания — после подтверждения отменить конкретный native yt-dlp и удалить его собственные файлы. Другая очередь и процессы остаются активными.

Reorder / drag/drop / download selected остаются заблокированными, добавление через Paste, + Add или Watch clipboard по-прежнему разрешено.

- Для удаляемого URL координатор выставляет tombstone и отменяет его token; отмена проверяется до запуска, во время чтения stdout/stderr yt-dlp и перед публикацией результата.
- Каждый cancellable job пишет файлы в **отдельную staging-директорию**. Отменённый URL теряет только собственные частичные файлы; успешные результаты публикуются с `OwnedPaths`.
- Удаление готового медиа использует **точный путь из результата/чекпоинта**, без wildcard, с проверкой принадлежности каталогу вывода. Любой симлинк/junction/reparse point в пути к root, его родителях или вложенных каталогах означает отказ операции.
- Публикация из staging запрещена при существующем целевом файле (иначе чужой файл можно ошибочно принять за скачанный и удалить при Remove). Предварительно проверяется весь batch и ссылки в staging. Никакой overwrite чужих файлов.
- Нативные security-тесты проверяют реальные NTFS junction, обход `../`, соседние каталоги, preexisting и сохраняют контрольные файлы снаружи неизменными.
- Оговорка безопасности: проверки выполняются непосредственно перед файловой операцией; при намеренной параллельной подмене путей остаётся класс TOCTOU. Если нужна полная защита от враждебной подмены directory handles, необходима отдельно реализованная handle-based Windows FS layer.
- Результат отмены — `Cancelled`, это не `Failed` и не `Completed`; в постоянную историю успехов он не пишется.
- Пока работник не подтвердил завершение и попытку очистки, строка сохраняет `PendingRemoval`. `CleanupError`, `CleanupPaths`, `StageDir` и исходный `RunDir` сохраняются в checkpoint; при ошибке очистки Remove должен оставаться доступен для повторной попытки. Нельзя удалять runDir, пока там есть неочищенные задания.
- Старый checkpoint может содержать `Engine` с `CancelDir`, `OutputRoot`, `RunDir` и `EventsPath`. Не считай старый `Path` доказательством владения; живой старый engine блокирует восстановление и новые сессии. После его завершения считываются корректные финальные Result-события с прежними границами очистки.
- Каждый результат/строка хранит исходный `OutputRoot`: изменение поля Output не меняет границы удаления старых результатов. Повторное добавление удалённого URL при том же engine сохраняется для следующего Start и не отправляется повторно в ingress.
- Event для уже удалённого URL не должен снова добавлять строку в GUI.
- Любой недостаток прав при удалении — явное предупреждение, строка остаётся для повторной попытки.
- Визуальное подтверждение требуется перед удалением начатых или завершённых файлов.

- Перед передачей нового URL проверяется общая история успехов; Cancel не меняет очередь.
- Новые ссылки передаются в `DownloadCoordinator.Add` через канал заданий и dedup по точному URL. UI второго экземпляра доставляет аргументы существующему окну по named pipe.
- Добавление после завершения движка сохраняется как `Queued` до следующего Start.
- Статус `Running` для новой ссылки выставляется при фактическом начале работы задания.
- Новые URL сохраняются в session checkpoint, а история успешных скачиваний продолжает пополняться из engine.

### Кодек — предпочтение

Для H264/VP9/AV1 format selector сначала пытается codec-specific вариант, затем generic fallback в рамках выбранного ограничения quality.

Не документируй и не реализуй это как строгий codec lock без отдельного изменения требований.

### Повторы только временных ошибок

Классификация находится в `src/VideoDownloader/Downloads/YtDlpOutputParser.cs`; решение о повторе выполняет `DownloadCoordinator`.

Не retry permanent/auth/unavailable ошибки бессмысленно. По умолчанию внешний backoff:

~~~text
5s, 10s, 20s
~~~

Максимальная задержка — 60 секунд.

## Подписки: текущий контракт

- Только ручные проверки и управление входящими. Не добавляй таймер, автоматическую проверку при старте, автоскачивание или Планировщик Windows без отдельной задачи; направления развития перечислены в [плане проекта](../project/ROADMAP.md).
- Исходная разметка окна — `src/VideoDownloader/UI/Views/SubscriptionsWindow.xaml`; в ZIP сохраняется путь `ui/SubscriptionsWindow.xaml`. Данные — `subscriptions.json` версии 1 в фактическом каталоге пользовательских данных. Логика — `SubscriptionStore` и `SubscriptionScanner`. Не смешивай файл подписок с `session.json` или постоянной историей.
- Порядок материалов подписки хранится существующим списком `SubscriptionSnapshot.Items`, без новой версии JSON. После успешного Full ставь текущие материалы в порядке `scan.Items`, отсутствующие исторические записи сохраняй в конце; RecentWindow ставит проверенное окно перед прежним хвостом. Сохраняй точные URL, состояния и порядок других подписок. Не сортируй «Входящие и результаты» по состоянию или DiscoveredAt и не включай пользовательскую сортировку колонок. Для старого накопленного снимка достаточно одной полной проверки, удаление данных не требуется. Проверяй перестановку, RecentWindow, исторический хвост, старый формат, отказ/отмену и сохранение состояний.
- Поле «URL подписки» выбранного источника должно оставаться read-only, но выделяемым для Ctrl+C; «Копировать URL» копирует исходный точный URL и доступно во время проверки. Смена выделения не должна оставлять адрес прежней подписки.
- Поддерживается любая HTTP(S)-коллекция, полностью перечисляемая текущим yt-dlp. Не вводи whitelist только YouTube. RSS/Atom — необязательное дополнение, с автоматическим определением YouTube-ленты по метаданным и ручным адресом ленты. Первая проверка всегда требует полного перечисления через yt-dlp; последующие Windows-проверки могут использовать проверенное окно по правилам ниже. Неизменившаяся RSS не заменяет проверку коллекции; ошибка ленты означает предупреждение, а не отказ от пригодного результата yt-dlp. RSS обогащает только точные URL из текущего результата обнаружения. Не добавляй feed-only элементы во входящие.
- В Windows обычная повторная ручная проверка использует окно до 20 новых публикаций только при Initialized и непустом снимке известных URL: для явных вкладок YouTube `/videos`, `/shorts`, `/streams` без query/fragment либо Pornhub с подтверждённой секцией самых новых публикаций. Корни YouTube-каналов, произвольные плейлисты и прочие источники проверяй полностью. Флажок «Полная проверка» принудительно отключает окно для текущего batch; начальный scan всегда полный.
- Результат окна имеет явный `SubscriptionScanScope.RecentWindow`, не служит доказательством полного архива и не устанавливает baseline. Принимай его только после проверки ответа и пересечения точных URL с накопленными материалами; без пересечения, при неизвестном порядке или непригодном ответе переходи к полному scan в том же deadline. Окно дополняет прежний снимок; старые материалы и состояния сохраняются. Для пересечения учитывай Baseline/New/Queued/Skipped/Processed/AlreadyProcessed, не только успешно скачанные URL. RSS дополняет только подтверждённые текущим результатом URL. LastSuccessUtc означает успешную проверку любого поддержанного scope. Probe ограничен 30 секундами YouTube / 45 секундами Pornhub внутри общего deadline, чтобы таймаут окна оставлял бюджет полному fallback; пользовательская отмена fallback не запускает.
- Размер окна 20 не является лимитом новинок. Отдельный fixture-сценарий 100 известных (в том числе Processed/Skipped) + 100 новых должен выполнить recent-запрос без якоря, затем полный обход, вернуть все 200 материалов и сохранить все 100 новых с прежними решениями старого набора. Дальнейшая явная постановка всех 100 в очередь не запускает дополнительное перечисление и скачивание.
- Обычный полный scan ограничен 10 000 элементами, 180 секундами и 32 МиБ stdout метаданных. Сборщик публикаций Pornhub имеет отдельный бюджет: 10 000 роликов, 500 страниц, 15 минут и те же 32 МиБ. RSS/Atom ограничена 2 МиБ и 12 секундами. Обрезанный список, превышенный предел, null/неидентифицируемый элемент, некорректный URL или ошибка перечисления запрещают считать scan полным. Не меняй baseline, items и LastSuccessUtc при таком сбое.
- Для полного перечисления используй отдельный отменяемый процесс yt-dlp с игнорированием внешней конфигурации и `--no-flat-playlist`: вложенные коллекции должны раскрываться до материалов. Нераскрытые `url`/`url_transparent` не являются материалами и запрещают успешный scan. Не используй PreviewService с выбором первого элемента плейлиста. Читай stdout/stderr параллельно, проверяй пределы и завершай только дерево процесса текущей проверки при отмене.
- Явное исключение: Pornhub `/channels|model|pornstar|users/<slug>` перечисляет упакованный `collection-plugins/videodownloader/yt_dlp_plugins/extractor/vd_pornhub.py` через `--no-plugin-dirs --plugin-dirs … --use-extractors videodownloader:pornhub:channel --flat-playlist`. Он обходит только публикации (`/videos` каналов, `/videos/upload` профилей), исключает историю/рекомендации, проверяет пагинацию и повторно первую страницу. Адаптер C# различает полный `vd_ph_scan` версии 1 и явный `vd_ph_recent` с `complete=false`, `scope=recent`, подтверждённым порядком и повтором первой страницы; проверяет согласованность страниц и уникальные watch URL. Последний принимается только как окно, произвольный flat JSON по-прежнему запрещён. Режим `recent_window=20` передаётся сборщику явно; без него сохраняется полный обход, в том числе для Android. Недоступное видео с известным URL становится самостоятельной задачей обычного движка. Канал не является успешным media-результатом. Не помещай плагин в автоматически загружаемый каталог `yt-dlp-plugins`; отдельный Python нужен только тестам разработчика, приложение загружает плагин внутри yt-dlp.exe.
- Локальная идентичность материала — `SubscriptionId` + точный URL (ordinal). Не группируй по media ID и не нормализуй произвольно параметры URL. Между подписками совпадение определяется тем же точным URL.
- Адаптеры обнаружения формируют адреса только новых материалов коллекции: Pornhub — `https://www.<base-site>/view_video.php?viewkey=<id>`; быстрое окно YouTube после строгой проверки YoutubeTab/source, 11-символьного ID и соответствующего ему watch/shorts/live URL — `https://www.youtube.com/watch?v=<id>`, как при полном YoutubeIE. Не переписывай прежние URL подписок, очереди или истории и не объединяй их по media ID: общая exact URL identity сохраняется.
- При проверке редиректов Pornhub `/videos/upload` и `/videos` одного kind/slug — допустимые адреса публикаций. Следующие страницы и повтор первой запрашивай по подтверждённому конечному endpoint, но `vd_ph_scan.listing_url` сохраняет исходный ожидаемый адрес для адаптеров. Не принимай главную страницу профиля как полный архив и не ослабляй проверки сайта, профиля, вкладки или номера страницы. Диагностика отклонённого перехода должна показывать URL назначения без credentials и произвольной query.
- Для вариантов разметки Pornhub допускаются также `claimedUploadedVideoSection`, `channelVideosList`, `showAllChanelVideos`, `ul#moreData.videos`, `div/section.videoUList` и карточки `videoblock`. Не принимай произвольный `moreData.feedItems`, все watch-ссылки документа или несколько независимых списков одной обёртки за полный архив. Карточки меню, боковых панелей и footer исключаются; история и рекомендации исключаются вместе со своей пагинацией. Основная пагинация может находиться в `nav`/`footer`: не теряй объявленные страницы из-за тега контейнера. Ошибка неизвестной страницы сообщает только адрес, структурные имена секций и счётчик карточек, без HTML, viewkey, произвольных query или cookies; распознанная страница проверки возраста объясняет использование Cookies.
- Если есть `section#videosTab`, ищи публикации только внутри неё: неизвестная разметка основной вкладки не разрешает fallback к распознанной сетке снаружи. Разбирай карточки, счётчики, пустое состояние и пагинацию по секциям; не смешивай их глобально. При наличии этой вкладки не принимай внешнюю ownerless-пагинацию/`rel=next`/`moreDataBtn` за её навигацию; основные `nav`/`footer` внутри вкладки по-прежнему обходятся. Вложенные обёртки не являются отдельными списками; одинаковые копии сверяй по полному набору ключей и счётчикам. Игнорируй пустые placeholders только без карточек, watch-ссылок, счётчика, empty-state marker, ошибок карточек и своей пагинации. Не выбирай между разными самостоятельными списками по порядку, размеру или специфичности селектора; ошибка сообщает ограниченный список структурных имён и размеров без viewkey. Идентичность выбранной секции проверяется на следующих страницах и повторе первой.
- Первая успешная проверка устанавливает baseline без очереди либо помечает весь существующий набор для очереди (`DownloadExisting`, `InitialQueuePending`) по явному выбору пользователя. Показывай все Baseline, включая старые записи, в «Входящие и результаты» как «Исходный снимок»; открытие списка не меняет состояние. Явное добавление выбранного Baseline разрешено той же командой очереди, без live ingress. Последующие новые URL получают состояние New. Незавершённое добавление исходного набора сохраняй до MarkQueued/Skip.
- Элементы подписки имеют состояния Baseline/New/Queued/Processed/AlreadyProcessed/Skipped. Реальный успешный результат движка или общая история успехов подтверждают обработку; обнаружение, добавление в очередь, baseline и Skip не являются успехом. Уведомление об уже обработанном URL из другой подписки показывай и подтверждай один раз, сохраняя DuplicateSubscriptionId/DuplicateNotified. Успех только из глобальной истории без известной другой подписки означает Processed без cross-subscription notice. SuccessAttributed сохраняет различие после перезапуска: true только для Processed с подтверждённым успехом ранее поставленного в очередь материала подписки; глобальный успех без такого источника оставляет false и не становится источником уведомления при будущих проверках.
- Добавление из подписок возвращает реально добавленные URL и отправляет их только в обычную очередь следующего Start. Не вызывай live Add/ingress во время текущей сессии. Не помечай не добавленные или отклонённые ссылки как Queued.
- После завершения всей ручной проверки предлагай один общий приём `New` успешно проверенных источников, включая ранее найденные и пока не принятые новинки. При «Проверить все» не показывай вопрос после каждой коллекции. Отказ и закрытие вопроса сохраняют `New`; отменённая проверка или закрытое окно не показывают предложение, источники с ошибкой исключаются. `Baseline`, `Skipped`, `Processed` и `AlreadyProcessed` в общий приём не входят; строки с `InitialQueuePending` обрабатывай отдельно существующим подтверждённым выбором `DownloadExisting`. После согласия перечитай снимок и историю, заново отфильтруй предложенные материалы по точным SubscriptionId+URL и используй обычное durable-подтверждение очереди. Модальный цикл не разрешает второй запуск проверки/приёма; `Queued` получают только действительно принятые ссылки. Само согласие не запускает Start. Проверяй один диалог на batch, Yes/No/Close, отказ и отмену, частично успешный batch, позднее изменение состояния и ошибку/частичный отказ очереди.
- Подписка имеет редактируемый ShortName. Пустое имя заполняй только при полном успешном scan из SuggestedName (канал/автор), иначе Title; после назначения не меняй его автоматически. Версию 1 без единственного нового поля ShortName читай с пустым значением, сохраняя строгую проверку остальных полей. Нормализация сохраняет прежние правила: один компонент Windows-пути, замена запрещённых символов/control, схлопывание пробелов, обрезка крайних точек/пробелов, предел 80 UTF-16 без разрыва surrogate pair, префикс для device names.
- Новые задания подписки сохраняют SubscriptionId и снимок SubscriptionName в session.json. Имя закрепляется при enqueue, базовый каталог — при Start: D:\Video\123, с Archive — D:\Video\yyyy-MM-dd\123. Переименование влияет только на будущие добавления; уже существующий URL очереди не переназначай. Старые checkpoint без полей означают обычное задание. Фиксируй фактический OutputRoot каждого задания для публикации/отмены/очистки; не подменяй его общим root сессии после успеха.
- Храни записи атомарно под общим mutex `Local\VideoDownloader.Subscriptions`; Read возвращает отделённый snapshot. Строго проверяй формат версии 1. При повреждённом JSON не перезаписывай и не пересоздавай файл. Удаление подписки не удаляет media, очередь и историю.
- Проверяй первый baseline/очередь и его видимость, окно 20 среди 100 известных, новинки с пересечением и без него, forced-full, сохранение состояний/прежнего снимка при отказе, повторное обнаружение, полноту и пределы scan, отказ/отмену, RSS fallback, exact URL, уведомление после реального успеха и однократное подтверждение, сохранность повреждённого JSON, очередь без live-add. Для совместимости используй фиксированные `tests/fixtures/legacy/`, без запуска второй реализации.

Прогресс проверки подписок показывается через XAML-карточку: текущий источник, этап, время, завершённые источники/всего, анимация активного обхода. Общая шкала считает реальные завершённые проверки, включая ошибки; отмена оставляет частичный результат. Не выдавай байты, время или неизвестное число материалов за процент готовности коллекции. Scanner сообщает необязательные этапы RecentWindow/FullFallback/Enumerating/Parsing/Feed/Ready, подтверждённое число материалов после разбора и фактические байты не чаще 4 раз/с. Ready означает готовность результата обхода, успех отображается только после применения пригодного результата с явным scope. Ошибка обработчика прогресса не должна менять итог/вывод сканера. Публикуй данные в Dispatcher; работник не обращается к WPF. Отложенные события не откатывают этап сохранения/очереди и игнорируются после смены источника, отмены, закрытия или нового запуска. Терминальный итог остаётся видимым; анимация и часы останавливаются.

## Сохранение и восстановление сессии

- `AppPersistence.AtomicWrite` повторяет только `File.Move` одного закрытого temp на Windows для кодов 5/32/33: задержки 15/30/60/120 мс. Не снимай ReadOnly/ACL и не удаляй старое назначение ради обхода отказа. Постоянная ошибка сохраняет старый файл и исходный тип/HResult. Проверяй настоящий временный/постоянный sharing lock и ReadOnly в `AtomicWriteTests`; polling-readers тестов используют `FileShare.ReadWrite | FileShare.Delete`. Ошибка сохранения должна оставлять в журнале тип/HResult/стек, сохраняя защиту read-only checkpoint.

- Очередь, конечные статусы и параметры сохраняются атомарно в `%LOCALAPPDATA%\\VideoDownloader\\session.json`, не в `%TEMP%`.
- Ни в коем случае не перезапускай успешно завершённые URL обычной кнопкой Start; ручной Retry допускается.
- При запуске восстановление требует явного подтверждения пользователя и никогда не начинает загрузку автоматически.
- Не перезапускай задания, пока ещё жив старый engine, сопоставляй PID с StartTime, чтобы защититься от PID reuse.
- При изменении checkpoint logic дополняй нативные regression-тесты и `LegacyCompatibilityTests`, проверяй реальные диалоги восстановления в Windows CI.

## Постоянная история успешных загрузок

- Все успешные URL записываются append-only в `%LOCALAPPDATA%\\VideoDownloader\\successful-downloads.jsonl`.
- `CompletedAtUtc` хранит время успеха; в диалог повтора передаётся последняя дата, а не дата импорта. Legacy-запись без времени остаётся с неизвестной датой.
- История независима от session checkpoint и удаления Queue: **никогда не очищай её** при завершении сеанса.
- Сравнение URL точное (ordinal), без сомнительной нормализации параметров.
- Перед **каждым** download start/explicit retry проверяй кандидатов в истории и применяй Yes/No/YesAll/NoAll. No удаляет соответствующий URL из Queue. Cancel/X не запускает процесс и не меняет очередь.
- Не записывай failed/cancelled URL как успешные; UI проверяет историю *до* запуска engine.
- Код завершения yt-dlp 0 недостаточен: успех требует существующего media path из `after_move:__VD_FILE__`. Внешние конфиги yt-dlp не должны менять параметры движка. Filename template проверяется до native launch: только относительные пути без компонентов `..`.
- Append истории под mutex поддерживает корректный последний JSON record без LF, но не изменяет повреждённый хвост.
- Используй межпроцессную синхронизацию истории и не проглатывай ошибки при чтении повреждённых данных.
- Проверяй append/даты/повреждения нативными regression-тестами, а все варианты решения о повторе — настоящими WPF-диалогами.

## Трей и цвета состояний

- Tooltip NotifyIcon.Text обновляется из session stats, содержит OK → Left → Err и скорость при активном скачивании; длина ограничена 63 символами.
- Queue и Downloads статусы раскрашиваются WPF DataTriggers по стабильному `Status`, а не по тексту ошибок или процентам.
- Цвета доступны в тёмной теме: completed=green, queued=grey, running=cyan, interrupted=amber, failed=red.

## WPF

- Queue по умолчанию 380 × 4/3 px; две настоящие GridSplitter меняют ширины Queue/Downloads/Preview. `QueuePanelWidth` и `PreviewPanelWidth` сохраняются в DownloadOptions без повышения версии session; Downloads занимает остаток. Проверяй восстановление старых/пустых сессий, нечисловые/слишком большие значения, минимальное окно и фактические Drag-события. Ширины не должны сбрасываться от смены профиля.
- ShowVideoTitlesCheck переключает подписи Queue/Downloads между Url и Title. По умолчанию и при неизвестном заголовке отображай URL; подсказки и действия всегда используют исходный точный URL. Сохраняй Settings.ShowVideoTitles и Queue.Title совместимо с прежними данными. Получай названия через существующий preview worker/кеш и Title-события, обновляя все соответствующие строки, включая невыбранные. Смена режима не запускает сеть, загрузку и дополнительные workers.

- основной UI framework — WPF/XAML;
- WinForms используется точечно для tray и стандартных dialogs;
- новые controls должны корректно выглядеть в dark theme;
- не полагайся на системные default templates для ComboBox/DataGrid, если они конфликтуют с dark UI;
- Queue/Downloads DataGrid read-only;
- двойной щелчок ЛКМ по строке Queue открывает существующий `Path` только у `Completed`; заголовок, пустое место, незавершённые строки и отсутствующие файлы не запускают shell или браузер. Открываемое приложение не помещай в job работника; ошибки запуска показывай без падения GUI;
- длительность сессии измеряй монотонно, начиная с Start и включая паузу. Фиксируй при завершении координатора после работников/очистки, сбрасывай при новом Start/Retry. Превью и ожидающая очередь до Start не запускают часы. Позднее завершение старой сессии не должно останавливать новую;
- возле Filename template сохраняй краткую подсказку и отдельную «Справка…» с синтаксисом, полями, примерами и текущими ограничениями относительного пути; справка не меняет шаблон и не запускает сеть;
- при изменении XAML обновляй smoke markers, если они отражают проверяемый контракт.

## Разработка и движок

- Для скриптов build/tests нужен PowerShell 7; используй `$ErrorActionPreference = 'Stop'`, явное разрешение путей и проверки обязательных файлов. Если сразу после интерполированной переменной идёт двоеточие, используй braces.
- Не блокируй UI thread сетевыми операциями; тяжёлые yt-dlp/dependency операции выполняй вне UI thread. Освобождай process/stream/http objects.
- `src/VideoDownloader/Downloads/DownloadCoordinator.cs` владеет активными заданиями, каналом очереди, отменой и конечной публикацией результата. Не разделяй согласованное завершение так, чтобы отмена гонялась с публикацией файлов и историей.
- `Threads` задаёт параллельность URL; `Fragments` передаётся как `yt-dlp -N`.
- Новый параметр добавляй в `DownloadOptions`, UI и построение аргументов; проверяй фактические аргументы дочернего процесса и обновляй [обзор](../../README.md) и [справочник Windows](../user/windows-reference.md).
- Сохраняй нативные тесты полного контракта аргументов, codec/quality fallback, отсутствия загрузки при preview и независимости полного scan.

## Сборка и состав пакета

Единственный Windows-проект приложения — `src/VideoDownloader/VideoDownloader.csproj`: Windows x64, .NET 8, WPF, автономный EXE. Пользователь запускает EXE напрямую. Обязательны соседние yt-dlp, XAML, ресурсы и `collection-plugins/`; единственный EXE не заменяет весь portable ZIP. Android собирается отдельно из `android/`, как описано выше.

`scripts/build.ps1 -Task Publish` создаёт `dist/native`, `dist/VideoDownloader-native.zip` и SHA-256. Параметры `-Version`, `-OutputDirectory`, `-ArchivePath`, `-ChecksumPath` позволяют main-only release job выбрать версию и имена файлов без второго упаковщика.

Пакет обязательно включает `collection-plugins/videodownloader/yt_dlp_plugins/extractor/vd_pornhub.py`; копируй только исходные `.py`, без `__pycache__`/`.pyc`. Проверка пакета должна отклонять CMD, `.ps1/.psm1`, `pwsh.exe` и launcher вместо приложения. Внешний Python пользователю не нужен.

## Тесты перед PR/merge

На Windows с .NET 8 SDK и PowerShell 7 выполни из корня:

~~~powershell
pwsh -NoProfile -File scripts/build.ps1 -Task Test
~~~

Команда собирает приложение и выполняет release-version/Russian/smoke, нативные unit/integration/security/legacy tests и реальные WPF-сценарии с изолированным профилем. Не подменяй холодное получение метаданных тестом с готовым кешем. Проверяй все пути добавления URL/TXT/InternetShortcut/подписка до Start без выбора строки, а также singleton/протокол/трей и все варианты диалога повтора.

Исполняемые проверки находятся в `tests/VideoDownloader.Tests/` и `tests/VideoDownloader.UiTests/`: `LegacyCompatibilityTests` читает фиксированные старые данные; `SubscriptionStoreTests` и `SubscriptionScannerTests` проверяют обнаружение, RSS и состояния; WPF host проверяет настоящие контролы. Не заменяй эти сценарии поиском маркеров в исходниках.

Для коллектора выполни `python tests/pornhub-collector-tests.py` с версией yt-dlp, закреплённой в Windows CI. Windows-тест адаптера дополнительно проверяет загрузку плагина настоящим упакованным `yt-dlp.exe` на офлайн-страницах. Живую проверку сайта описывай отдельно и не выдавай фикстуры за доступ к реальному каналу.

Если менялась упаковка:

~~~powershell
pwsh -NoProfile -File scripts/build.ps1 -Task Publish
~~~

Для изменений Windows-кода, тестов, скриптов и сборки Windows workflow `native-windows.yml` должен быть зелёным перед merge. Для Android-кода обязателен `android.yml`; изменения общих `collection-plugins/` и `tests/fixtures/portable-queue/` проверяются обеими платформами. Smoke проверяет синтаксис скриптов разработки, XAML и обязательные файлы/контролы; функциональные проверки выполняют C#-тесты. PR только с Markdown может не запускать workflow из-за фильтра путей: перед его merge проверь ссылки, якоря, Mermaid и соответствие инструкций исходникам. После push в `main` полный Windows workflow запускается независимо от состава изменений.
