# Направления развития

Это предложения для будущей разработки, а не список уже доступных функций. Основа — Windows и Android в коммите `3f3b929` после объединения PR #54. Текущее поведение описано в [руководствах пользователя](../user/README.md), устройство проекта — в [архитектуре](../developer/architecture.md).

Развитие сохраняет C# / .NET 8 / WPF для Windows, Kotlin / Compose для Android, yt-dlp и FFmpeg. Пользовательского CLI нет. Планировщик Windows, если он будет реализован, потребует отдельного ограниченного режима проверки; такого режима сейчас нет.

## Что уже реализовано

- URL, импорт списка и обычная очередь с ручным `Start`; история подтверждённых успешных загрузок.
- Ручные подписки на HTTP(S)-коллекции, которые текущий yt-dlp может полностью перечислить в установленных пределах. При добавлении можно оставить существующие материалы исходным набором либо поставить их в очередь.
- RSS/Atom как дополнение названий точных URL, подтверждённых yt-dlp. Лента не заменяет проверку коллекции и не добавляет самостоятельные материалы.
- Краткое имя и отдельная подпапка подписки, получение метаданных и до 15 изображений превью, общий формат переноса очереди `VDQUEUE1:` / `.vdqueue`.
- В Windows — проверенное окно до 20 последних публикаций для отдельных источников с полным обходом при необходимости, общее предложение поставить новинки в очередь, сведения и превью материала подписки, четыре профиля журнала.
- В Android — foreground service для загрузок после сворачивания, MediaStore/SAF, резервная копия и APK-артефакты CI. Мобильный клиент пока не повторяет все расширенные сценарии Windows.

Окно 20 не ограничивает число найденных новинок: при отсутствии знакомого URL Windows выполняет полный обход в пределах лимитов. Эти гарантии нужно сохранить при развитии и перенести в Android.

## Правила подписки: подробности R4

Фильтры можно развивать по дате, длительности, названию, доступности и типу публикации. Отсутствующее значение не должно молча исключать видео: предварительный просмотр отдельно показывает подходящие, исключённые и требующие решения материалы, а также причину.

Индивидуальные профиль, базовый каталог и шаблон имени закрепляются в момент, определённый контрактом очереди. Уже работающая подпапка по краткому имени сохраняется. Изменение подписки влияет на будущие задания; перенос ранее скачанных файлов требует отдельного действия. Пакетное применение правил не меняет историю успеха. Для пропущенных и ранее недоступных материалов нужно явное повторное рассмотрение.

## Проверки по расписанию: подробности R10

Первая ступень — проверки, пока приложение открыто. Интервал каждой подписки и разрешение проверки при запуске настраиваются отдельно и изначально выключены. После сна пропущенные проверки выполняются последовательно с ограничением общей параллельности и частоты запросов к одному сайту. Один источник не проверяется одновременно несколько раз.

В интерфейсе нужны следующая проверка, история попыток и различимые состояния временного сбоя, ограничения сайта и необходимости обновить cookies. Отмена, сон и перезапуск не заменяют успешный снимок частичным. Проверка не блокирует UI и загрузки; обнаружение по-прежнему не означает разрешения скачивать.

## Планировщик Windows: отдельная задача R11

Планировщик остаётся в бэклоге. Запуск без открытого GUI не реализован, и наличие Windows foreground/tray-режима не решает эту задачу.

- Создание, изменение и удаление задания выполняются только по явному действию пользователя. Начальный вариант — текущий пользователь и запуск при входе в Windows.
- Нужны фактический каталог данных и доступ к cookies в контексте того же пользователя.
- Открытый GUI и фоновая проверка согласуются через общую блокировку и отдельные входящие. Два процесса не перезаписывают `session.json` одновременно.
- Перемещение portable EXE требует восстановления регистрации; недоступный прежний путь даёт понятное предупреждение.
- Результаты и ошибки доступны при следующем открытии приложения. Пробуждение компьютера и сетевые условия задаются отдельно.

Первый выпуск такого задания только обнаруживает материалы. Автоматическое скачивание — R12 с отдельным разрешением и политикой. Возвращать универсальный пользовательский CLI или создавать постоянно работающий сервис для этого не требуется.

## Автоматическое скачивание: отдельная задача R12

Перед включением пользователь должен видеть, какие материалы правила выберут сейчас и как будет обработан старый исходный набор. Разрешение задаётся для каждой подписки; по умолчанию сохранён ручной режим.

Обязательны лимиты числа заданий, суммарного объёма, свободного места и нагрузки, временные окна, политика временных повторов и явная остановка при ошибке доступа. Премьеры и трансляции, ставшие доступными позднее, требуют понятной политики повторного обнаружения. Постановка, отмена, публикация и восстановление согласуются с обычной очередью; история подтверждается только после успешного результата.

## Этапы работы

1. **Общее поведение.** Выполнить R1 по четырём этапам Android, одновременно поддерживая R2. Итог — проверенная матрица различий, сохранность прежних данных и реальные фоновые сценарии.
2. **Большие очереди и подписки.** R3–R5. Итог — пользователь может найти и принять нужное, заранее увидеть действие правил и сохранить контроль через `Start`.
3. **Диагностика и хранение.** R6–R8. Итог — понятна причина сбоя, найден готовый файл, служебные данные очищаются без потери истории и чужих файлов.
4. **Доступность и распространение.** R9 и R13. Итог — проверены клавиатура/TalkBack/масштаб и обновление Android поверх установленной версии с постоянной подписью.
5. **Управляемая автоматизация.** R10, затем отдельные R11 и R12. Итог каждого шага проверяется самостоятельно; расписание и скачивание включаются раздельно.

Каждый этап оформляется отдельными небольшими MR с применимыми [проверками](../developer/testing.md). Планы не подменяют пользовательскую документацию: руководство обновляется только после появления и проверки поведения.
