# AGENTS.md

Инструкции для coding agents, работающих с этим репозиторием.

## Цель проекта

Video Downloader — Windows-приложение на **C# / .NET 8 / WPF** с одной пользовательской UI-версией.

- Точка запуска — `VideoDownloader.exe`; пользовательского CLI, CMD-launcher и резервного GUI нет.
- Единственный проект приложения: `src/VideoDownloader/VideoDownloader.csproj`. Окна и XAML находятся в `src/VideoDownloader/UI/Views/`, владельцы состояния — в `src/VideoDownloader/UI/Controllers/`.
- Модели и entry point находятся в корне проекта; загрузки, превью, подписки, хранение и совместимость разделены по `Downloads/`, `Preview/`, `Subscriptions/`, `Persistence/`, `Compatibility/`; Windows-процессы — в `Infrastructure/Windows/`.
- C# unit/integration-тесты: `tests/VideoDownloader.Tests/`; настоящие WPF-сценарии: `tests/VideoDownloader.UiTests/`. Оба проекта ссылаются на приложение через ProjectReference. Не включай тестовые partial-классы, сценарии или переключатели запуска тестов в релизный EXE.
- Единые команды build/test/publish: `scripts/build.ps1`. PowerShell нужен разработке и CI, не приложению.
- Релизный ZIP автономен: пользователь не устанавливает PowerShell, Python или .NET Runtime.
- Сохраняй чтение прежних пользовательских данных в `%LOCALAPPDATA%\VideoDownloader`, включая финальные Result-события и защиту от живого старого работника `pwsh`.

## Автоматические стабильные GitHub Releases

Любой коммит в `main` после успешного native Windows CI публикуется как **стабильный GitHub Release**. Отдельный job `release` в `.github/workflows/native-windows.yml` автоматически создаёт следующий Git-тег `v2.0.N`, готовый Windows ZIP и SHA-256, генерирует Release Notes. Публикация для PR **запрещена**: минимальные permissions по умолчанию `contents: read`, запись только в main-only release job.

- Нумерация `.github/scripts/ReleaseVersion.psm1`; перед merge выполняй `scripts/release-version-tests.ps1` в составе общей команды Test.
- Публикуемые EXE и Git-тег должны иметь одинаковый номер версии; параметры publish переопределяют версию проекта.
- Release никогда не должен публиковаться, если падают native unit/integration/UI/security tests.
- Не изменяй и не удаляй чужие / ранее опубликованные релизы, существующий draft `v1.0.0` не трогай.
- Main означает релизную готовность: перед merge требуется проверка API и интерфейсной совместимости.
- Политика выпуска: [RELEASING.md](RELEASING.md).

## Основная C#-архитектура

WPF-интерфейс и движок расположены в `src/VideoDownloader/`, два тестовых проекта — в `tests/`. Релизный ZIP создаётся workflow `native-windows.yml`.
Пользовательская сборка не должна включать CMD/PowerShell-скрипты или запускать `pwsh.exe`. URL, TXT, InternetShortcut и `videodownloader://` передаются в интерфейс; второй экземпляр использует singleton и named pipe и возвращает существующее окно из трея.

При изменениях в `src/VideoDownloader/`:
- Запускай native Windows CI: сборка, открытие окна WPF, реальные Add/Remove,
  clipboard-preview, .url import и checkpoint через изолированный UI-тест.
- Запускай офлайн тесты реального `yt-dlp.exe`: параллельная загрузка,
  queued/running cancellation, late live Add, pause/resume.
- При отмене URL используй tombstone и синхронизацию конечного результата:
  публикация и удаление файлов должны быть согласованы, без оставшихся media.
- `DownloadItem` сохраняет прежние `PendingRemoval`, `CleanupError`,
  `CleanupPaths`, `StageDir`, `RunDir`, `AttemptFinished`, `DeferredToNextStart`.
  Не удаляй активную строку до подтверждения работника. Ошибка очистки и
  частичный манифест переживают checkpoint, Clear Queue и обновление приложения;
  Start/Retry исключают такие строки. Полный список опубликованных файлов
  сохраняется даже при неудачном rollback; меняй списки атомарной заменой,
  чтобы сериализация GUI не гонялась с изменением коллекции работником.
- Старый Result не применяется к `DeferredToNextStart`. Сохраняй контекст
  очистки и исходный `OutputRoot` также при чтении legacy Result-событий.
- Успех требует валидного `after_move:__VD_FILE__` media path из staging;
  код 0 без медиа не должен публиковать sidecars или пополнять историю.
- Счётчики transfer учитывают сброс при retry; постоянная HTTP/auth ошибка
  имеет приоритет над transient-подсказками в том же diagnostic.
- Операции удаления разрешены только с известным `OwnedPaths`; неизвестный
  путь из старого checkpoint сам по себе **не является доказательством владения**.
- Относись к C# `session.json`, `successful-downloads.jsonl`, preview cache
  как к совместимым с ранее использованными форматами.
- Из старого `Engine.EventsPath` читай финальные Result-события: старый GUI
  мог умереть до сохранения checkpoint. Активный legacy `pwsh` блокирует
  восстановление и новые native sessions.
- При `Archive` фиксируй каталог назначения на всю сессию; ночной переход
  даты не должен менять место публикации и удаления.
- Создавай native процессы загрузки, превью и сканирования yt-dlp через `ManagedChildProcess`: индивидуальный job назначается атомарно через `PROC_THREAD_ATTRIBUTE_JOB_LIST`; наследуются только явные pipe handles. Не помещай GUI или открываемые пользователем приложения в job работника. `yt-dlp -U` запускается отдельно: его штатная отложенная очистка `.old` должна пережить выход обновляющего процесса. Проверяй аварийный выход владельца, потомков, независимый процесс, аргументы, окружение и оба pipe в Windows CI.
- До запуска загрузок UI проверяет FFmpeg/ffprobe. Выбранный контейнер требует и merge, и remux; native-публикация проверяет расширение результата.
- После модального подтверждения live Add повторно проверяй наличие URL и идентичность активной сессии. Повторный вход не создаёт дубликат; завершённая или заменённая сессия оставляет ссылку для следующего Start. Проверяй это реальными вложенными WPF-диалогами.
- Границы вывода поддерживают корень диска/UNC с одним завершающим separator; сам root не считается дочерним файлом.
- Разрешённая повторная загрузка выбирает свободный суффикс для всего batch media/sidecars. `OwnedPaths` содержит только новые файлы. Helper без явного `renameCollisions` продолжает отклонять существующий destination; никакой overwrite. Планирование и публикация параллельных заданий согласованы; гонка с внешним процессом не разрешает перезапись чужого файла.
- Не запускай таймеры до восстановления. `SaveCheckpoint` блокируется на всём протяжении диалогов восстановления; ошибка чтения переводит checkpoint в read-only до показа предупреждения. Настройки восстанавливаются при пустой/завершённой очереди и при отказе от восстановления строк. Установка FFmpeg имеет общий шестиминутный deadline скачивания, включая тело при `ResponseHeadersRead`; timeout/cancel удаляет scratch и освобождает кнопки зависимостей.
- Для полной защиты от намеренной TOCTOU-подмены каталогов понадобится
  handle-based Win32 реализация; текущая проверка reparse/junction не даёт
  такой абсолютной гарантии.

Схемы взаимодействия компонентов и совместимость данных описаны в
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), правила выпуска — в
[RELEASING.md](RELEASING.md).

## Архитектурные инварианты

### 1. Progress должен оставаться machine-readable

Не возвращай парсинг обычных строк <code>[download] ...</code> как основной механизм прогресса.

Engine использует:

- <code>--progress-template</code> с <code>__VD_PROGRESS__</code>;
- <code>--print before_dl:__VD_TITLE__:</code>;
- <code>--print after_move:__VD_FILE__:</code>.

Структурированный вывод разбирается в `src/VideoDownloader/Downloads/YtDlpOutputParser.cs`, аргументы строит `YtDlpArguments` в том же каталоге. Согласованное завершение, отмена, публикация и очистка остаются в `DownloadCoordinator`.

Human-readable stdout допустимо анализировать только для вспомогательных событий вроде merge/error diagnostics.

`--progress` обязателен вместе с `--print`. Stdout/stderr читаются параллельно. UI показывает progress/скорость/объём/ETA в обеих таблицах. Result не должен повторно прибавлять размер файла к уже учтённому session transfer volume. При чтении старых JSONL-событий не принимай неполный или некорректный Result за терминальный результат; процент прогресса сам по себе не доказывает успех.

### 2. Preview prefetch-ится заранее

URL должен попадать в preview-prefetch queue сразу после добавления в Queue.

Контракт:

- один независимый background preview worker;
- Clipboard URLs во время загрузки получают приоритет в очереди prefetch, а ручной Paste сразу показывает выбранную ссылку в preview панели; Watch clipboard не крадёт текущее выделение;
- metadata + thumbnail запрашиваются заранее;
- клик по строке читает cache;
- если preview ещё не готов, клик только повышает приоритет URL;
- клик не создаёт второй тяжёлый metadata request;
- persistent cache: <code>%LOCALAPPDATA%\VideoDownloader\preview-cache</code>;
- TTL: **72 часа**;
- cache key: SHA-256 URL.

Получение и кеширование реализованы в `src/VideoDownloader/Preview/PreviewService.cs`.

Общий deadline запроса — 30 секунд, включая дочерний процесс,
заголовки и тело изображения. Для миниатюры дополнительно действуют 12 секунд
и предел 2 МБ. Таймаут метаданных завершает дочерний процесс и освобождает
единственного работника; ошибка изображения сохраняет текстовые метаданные.
Используй отдельный token для всего чтения тела при ResponseHeadersRead.

Название из SubscriptionItem переносится в main queue до preview; при восстановлении очереди пустые/URL-placeholder названия дополняются одним bulk-чтением подписок по точным SubscriptionId+Url. Ошибка необязательного файла подписок не блокирует восстановление обычной очереди. Preview с пустым заголовком не стирает известное название. Не определяй пригодность миниатюры только по суффиксу URL; проверяй байты, ограничивай весь набор кандидатов одним бюджетом и используй существующий FFmpeg для WebP/AVIF. Конвертер читает только собственный локальный scratch, ограничивает память/выход и отменяется вместе с запросом. Старая точная ошибка фильтра JPEG/PNG не должна удерживать пустую обложку в кеше 72 часа.

До принятия обложки проверяй реальное декодирование кадра, а не только сигнатуру; некорректный кандидат не блокирует запасной. Исходный кадр ограничен 16 777 216 пикселями, декодируемый растр — 720 по большей стороне без увеличения. Проверяй изображения при чтении дискового кеша; проверенную память не декодируй повторно при каждой постановке URL. Кеш использует точное ordinal-сравнение URL, включая проверку identity памяти. Ошибка записи кеша не должна отбрасывать полученные данные из памяти и панели. Полный сбой метаданных сообщает URL и причину интерфейсу, завершает состояние загрузки, сохраняет известное название и не меняет превью другой ссылки. Обогащение уже существующей строки из подписки сразу обновляет только заголовок текущего совпадающего превью без сетевого запроса.

Профили задают полный набор параметров: качество,
кодек, контейнер, AudioOnly, Archive, субтитры и встраивание данных. Только
«Архив 4K» включает Archive; остальные профили сбрасывают его. Пути, cookies,
скорость и число работников не меняются при выборе профиля.

### 3. Queue selectable во время download session

Во время активной загрузки пользователь должен иметь возможность:

- выбирать строки;
- смотреть preview;
- open/copy URL.

Во время активной сессии **Remove разрешён**: пользователь может убрать URL из очереди, а для уже начатого/законченного задания — после подтверждения отменить конкретный native yt-dlp и удалить его собственные файлы. Другая очередь и процессы остаются активными.

Reorder / drag/drop / download selected остаются заблокированными, добавление через Paste, + Add или Watch clipboard по-прежнему разрешено.

- Для удаляемого URL координатор выставляет tombstone и отменяет его token; отмена проверяется до запуска, во время чтения stdout/stderr yt-dlp и перед публикацией результата.
- Каждый cancellable job пишет файлы в **отдельную staging-директорию**. Отменённый URL теряет только собственные частичные файлы; успешные результаты публикуются с `OwnedPaths`.
- Удаление готового медиа использует **точный путь из результата/чекпоинта**, без wildcard, с проверкой принадлежности каталогу вывода. Любой симлинк/junction/reparse point в пути к root, его родителях или вложенных каталогах означает отказ операции.
- Публикация из staging запрещена при существующем целевом файле (иначе чужой файл можно ошибочно принять за скачанный и удалить при Remove). Предварительно проверяется весь batch и ссылки в staging. Никакой overwrite чужих файлов.
- Нативные security-тесты проверяют реальные NTFS junction, обход `../`, соседние каталоги, preexisting и сохраняют контрольные файлы снаружи неизменными.
- Оговорка безопасности: проверки выполняются непосредственно перед файловой операцией; при намеренной параллельной подмене путей остаётся класс TOCTOU. Если нужна полная защита от враждебной подмены directory handles, необходима отдельно реализованная handle-based Windows FS layer.
- Результат отмены — `Cancelled`, это не `Failed` и не `Completed`; в постоянную историю успехов он не пишется.
- Пока работник не подтвердил завершение и попытку очистки, строка сохраняет `PendingRemoval`. `CleanupError`, `CleanupPaths`, `StageDir` и исходный `RunDir` сохраняются в checkpoint; при ошибке очистки Remove должен оставаться доступен для повторной попытки. Нельзя удалять runDir, пока там есть неочищенные задания.
- Старый checkpoint может содержать `Engine` с `CancelDir`, `OutputRoot`, `RunDir` и `EventsPath`. Не считай старый `Path` доказательством владения; живой старый engine блокирует восстановление и новые сессии. После его завершения считываются корректные финальные Result-события с прежними границами очистки.
- Каждый результат/строка хранит исходный `OutputRoot`: изменение поля Output не меняет границы удаления старых результатов. Повторное добавление удалённого URL при том же engine сохраняется для следующего Start и не отправляется повторно в ingress.
- Event для уже удалённого URL не должен снова добавлять строку в GUI.
- Любой недостаток прав при удалении — явное предупреждение, строка остаётся для повторной попытки.
- Визуальное подтверждение требуется перед удалением начатых или завершённых файлов.

- Перед передачей нового URL проверяется общая история успехов; Cancel не меняет очередь.
- Новые ссылки передаются в `DownloadCoordinator.Add` через канал заданий и dedup по точному URL. UI второго экземпляра доставляет аргументы существующему окну по named pipe.
- Добавление после завершения движка сохраняется как `Queued` до следующего Start.
- Статус `Running` для новой ссылки выставляется при фактическом начале работы задания.
- Новые URL сохраняются в session checkpoint, а история успешных скачиваний продолжает пополняться из engine.

### 4. Codec — preference, не strict lock

Для H264/VP9/AV1 format selector сначала пытается codec-specific вариант, затем generic fallback в рамках выбранного ограничения quality.

Не документируй и не реализуй это как строгий codec lock без отдельного изменения требований.

### 5. Retry только transient ошибок

Классификация находится в `src/VideoDownloader/Downloads/YtDlpOutputParser.cs`; решение о повторе выполняет `DownloadCoordinator`.

Не retry permanent/auth/unavailable ошибки бессмысленно. По умолчанию внешний backoff:

~~~text
5s, 10s, 20s
~~~

Максимальная задержка — 60 секунд.

## Подписки: текущий контракт

- Только ручные проверки и управление входящими. Не добавляй таймер, автоматическую проверку при старте, автоскачивание или Планировщик Windows без отдельной задачи; дальнейшие этапы перечислены в `BACKLOG.md`.
- Исходная разметка окна — `src/VideoDownloader/UI/Views/SubscriptionsWindow.xaml`; в ZIP сохраняется путь `ui/SubscriptionsWindow.xaml`. Данные — `subscriptions.json` версии 1 в фактическом каталоге пользовательских данных. Логика — `SubscriptionStore` и `SubscriptionScanner`. Не смешивай файл подписок с `session.json` или постоянной историей.
- Поддерживается любая HTTP(S)-коллекция, полностью перечисляемая текущим yt-dlp. Не вводи whitelist только YouTube. RSS/Atom — необязательное дополнение, с автоматическим определением YouTube-ленты по метаданным и ручным адресом ленты. Полное перечисление через yt-dlp обязательно даже при неизменившейся RSS; ошибка ленты означает предупреждение, а не отказ от успешного полного результата. Состав подписки определяет полный список; RSS обогащает только точные URL из него. Не добавляй feed-only элементы во входящие.
- Обычный полный scan ограничен 10 000 элементами, 180 секундами и 32 МиБ stdout метаданных. Сборщик публикаций Pornhub имеет отдельный бюджет: 10 000 роликов, 500 страниц, 15 минут и те же 32 МиБ. RSS/Atom ограничена 2 МиБ и 12 секундами. Обрезанный список, превышенный предел, null/неидентифицируемый элемент, некорректный URL или ошибка перечисления запрещают считать scan полным. Не меняй baseline, items и LastSuccessUtc при таком сбое.
- Для полного перечисления используй отдельный отменяемый процесс yt-dlp с игнорированием внешней конфигурации и `--no-flat-playlist`: вложенные коллекции должны раскрываться до материалов. Нераскрытые `url`/`url_transparent` не являются материалами и запрещают успешный scan. Не используй PreviewService с выбором первого элемента плейлиста. Читай stdout/stderr параллельно, проверяй пределы и завершай только дерево процесса текущей проверки при отмене.
- Явное исключение: Pornhub `/channels|model|pornstar|users/<slug>` перечисляет упакованный `collection-plugins/videodownloader/yt_dlp_plugins/extractor/vd_pornhub.py` через `--no-plugin-dirs --plugin-dirs … --use-extractors videodownloader:pornhub:channel --flat-playlist`. Он обходит только публикации (`/videos` каналов, `/videos/upload` профилей), исключает историю/рекомендации, проверяет пагинацию и повторно первую страницу. Адаптер C# принимает только полный `vd_ph_scan` версии 1 с согласованными страницами и уникальными проверенными watch URL; произвольный flat JSON по-прежнему запрещён. Недоступное видео с известным URL становится самостоятельной задачей обычного движка. Канал не является успешным media-результатом. Не помещай плагин в автоматически загружаемый каталог `yt-dlp-plugins`; отдельный Python нужен только тестам разработчика, приложение загружает плагин внутри yt-dlp.exe.
- Локальная идентичность материала — `SubscriptionId` + точный URL (ordinal). Не группируй по media ID и не нормализуй произвольно параметры URL. Между подписками совпадение определяется тем же точным URL.
- Сборщик Pornhub выдаёт канонические `https://www.<base-site>/view_video.php?viewkey=<id>` только для вновь обнаруженных публикаций. Это не меняет exact URL semantics существующей очереди, истории и других подписок.
- При проверке редиректов Pornhub `/videos/upload` и `/videos` одного kind/slug — допустимые адреса публикаций. Следующие страницы и повтор первой запрашивай по подтверждённому конечному endpoint, но `vd_ph_scan.listing_url` сохраняет исходный ожидаемый адрес для адаптеров. Не принимай главную страницу профиля как полный архив и не ослабляй проверки сайта, профиля, вкладки или номера страницы. Диагностика отклонённого перехода должна показывать URL назначения без credentials и произвольной query.
- Для вариантов разметки Pornhub допускаются также `claimedUploadedVideoSection`, `channelVideosList`, `showAllChanelVideos`, `ul#moreData.videos`, `div/section.videoUList` и карточки `videoblock`. Не принимай произвольный `moreData.feedItems`, все watch-ссылки документа или несколько независимых списков одной обёртки за полный архив. Карточки меню, боковых панелей и footer исключаются; история и рекомендации исключаются вместе со своей пагинацией. Основная пагинация может находиться в `nav`/`footer`: не теряй объявленные страницы из-за тега контейнера. Ошибка неизвестной страницы сообщает только адрес, структурные имена секций и счётчик карточек, без HTML, viewkey, произвольных query или cookies; распознанная страница проверки возраста объясняет использование Cookies.
- Если есть `section#videosTab`, ищи публикации только внутри неё: неизвестная разметка основной вкладки не разрешает fallback к распознанной сетке снаружи. Разбирай карточки, счётчики, пустое состояние и пагинацию по секциям; не смешивай их глобально. При наличии этой вкладки не принимай внешнюю ownerless-пагинацию/`rel=next`/`moreDataBtn` за её навигацию; основные `nav`/`footer` внутри вкладки по-прежнему обходятся. Вложенные обёртки не являются отдельными списками; одинаковые копии сверяй по полному набору ключей и счётчикам. Игнорируй пустые placeholders только без карточек, watch-ссылок, счётчика, empty-state marker, ошибок карточек и своей пагинации. Не выбирай между разными самостоятельными списками по порядку, размеру или специфичности селектора; ошибка сообщает ограниченный список структурных имён и размеров без viewkey. Идентичность выбранной секции проверяется на следующих страницах и повторе первой.
- Первая успешная проверка устанавливает baseline без очереди либо помечает весь существующий набор для очереди (`DownloadExisting`, `InitialQueuePending`) по явному выбору пользователя. Последующие новые URL получают состояние New. Незавершённое добавление исходного набора сохраняй до MarkQueued/Skip.
- Элементы подписки имеют состояния Baseline/New/Queued/Processed/AlreadyProcessed/Skipped. Реальный успешный результат движка или общая история успехов подтверждают обработку; обнаружение, добавление в очередь, baseline и Skip не являются успехом. Уведомление об уже обработанном URL из другой подписки показывай и подтверждай один раз, сохраняя DuplicateSubscriptionId/DuplicateNotified. Успех только из глобальной истории без известной другой подписки означает Processed без cross-subscription notice. SuccessAttributed сохраняет различие после перезапуска: true только для Processed с подтверждённым успехом ранее поставленного в очередь материала подписки; глобальный успех без такого источника оставляет false и не становится источником уведомления при будущих проверках.
- Добавление из подписок возвращает реально добавленные URL и отправляет их только в обычную очередь следующего Start. Не вызывай live Add/ingress во время текущей сессии. Не помечай не добавленные или отклонённые ссылки как Queued.
- Подписка имеет редактируемый ShortName. Пустое имя заполняй только при полном успешном scan из SuggestedName (канал/автор), иначе Title; после назначения не меняй его автоматически. Версию 1 без единственного нового поля ShortName читай с пустым значением, сохраняя строгую проверку остальных полей. Нормализация сохраняет прежние правила: один компонент Windows-пути, замена запрещённых символов/control, схлопывание пробелов, обрезка крайних точек/пробелов, предел 80 UTF-16 без разрыва surrogate pair, префикс для device names.
- Новые задания подписки сохраняют SubscriptionId и снимок SubscriptionName в session.json. Имя закрепляется при enqueue, базовый каталог — при Start: D:\Video\123, с Archive — D:\Video\yyyy-MM-dd\123. Переименование влияет только на будущие добавления; уже существующий URL очереди не переназначай. Старые checkpoint без полей означают обычное задание. Фиксируй фактический OutputRoot каждого задания для публикации/отмены/очистки; не подменяй его общим root сессии после успеха.
- Храни записи атомарно под общим mutex `Local\VideoDownloader.Subscriptions`; Read возвращает отделённый snapshot. Строго проверяй формат версии 1. При повреждённом JSON не перезаписывай и не пересоздавай файл. Удаление подписки не удаляет media, очередь и историю.
- Проверяй первый baseline/очередь, повторное обнаружение, полноту и пределы scan, отказ/отмену, RSS fallback, exact URL, уведомление после реального успеха и однократное подтверждение, сохранность повреждённого JSON, очередь без live-add. Для совместимости используй фиксированные `tests/fixtures/legacy/`, без запуска второй реализации.

Прогресс проверки подписок показывается через XAML-карточку: текущий источник, этап, время, завершённые источники/всего, анимация активного обхода. Общая шкала считает реальные завершённые проверки, включая ошибки; отмена оставляет частичный результат. Не выдавай байты, время или неизвестное число материалов за процент готовности коллекции. Scanner сообщает необязательные этапы Enumerating/Parsing/Feed/Ready, подтверждённое число материалов после разбора и фактические байты не чаще 4 раз/с. Ready означает готовность результата обхода, успех отображается только после применения полного результата. Ошибка обработчика прогресса не должна менять итог/вывод сканера. Публикуй данные в Dispatcher; работник не обращается к WPF. Отложенные события не откатывают этап сохранения/очереди и игнорируются после смены источника, отмены, закрытия или нового запуска. Терминальный итог остаётся видимым; анимация и часы останавливаются.

## Session checkpoint

- Очередь, конечные статусы и параметры сохраняются атомарно в `%LOCALAPPDATA%\\VideoDownloader\\session.json`, не в `%TEMP%`.
- Ни в коем случае не перезапускай успешно завершённые URL обычной кнопкой Start; ручной Retry допускается.
- При запуске восстановление требует явного подтверждения пользователя и никогда не начинает загрузку автоматически.
- Не перезапускай задания, пока ещё жив старый engine, сопоставляй PID с StartTime, чтобы защититься от PID reuse.
- При изменении checkpoint logic дополняй нативные regression-тесты и `LegacyCompatibilityTests`, проверяй реальные диалоги восстановления в Windows CI.

## Global successful-download history

- Все успешные URL записываются append-only в `%LOCALAPPDATA%\\VideoDownloader\\successful-downloads.jsonl`.
- `CompletedAtUtc` хранит время успеха; в диалог повтора передаётся последняя дата, а не дата импорта. Legacy-запись без времени остаётся с неизвестной датой.
- История независима от session checkpoint и удаления Queue: **никогда не очищай её** при завершении сеанса.
- Сравнение URL точное (ordinal), без сомнительной нормализации параметров.
- Перед **каждым** download start/explicit retry проверяй кандидатов в истории и применяй Yes/No/YesAll/NoAll. No удаляет соответствующий URL из Queue. Cancel/X не запускает процесс и не меняет очередь.
- Не записывай failed/cancelled URL как успешные; UI проверяет историю *до* запуска engine.
- Код завершения yt-dlp 0 недостаточен: успех требует существующего media path из `after_move:__VD_FILE__`. Внешние конфиги yt-dlp не должны менять параметры движка. Filename template проверяется до native launch: только относительные пути без компонентов `..`.
- Append истории под mutex поддерживает корректный последний JSON record без LF, но не изменяет повреждённый хвост.
- Используй межпроцессную синхронизацию истории и не проглатывай ошибки при чтении повреждённых данных.
- Проверяй append/даты/повреждения нативными regression-тестами, а все варианты решения о повторе — настоящими WPF-диалогами.

## Tray status / state colors

- Tooltip NotifyIcon.Text обновляется из session stats, содержит OK → Left → Err и скорость при активном скачивании; длина ограничена 63 символами.
- Queue и Downloads статусы раскрашиваются WPF DataTriggers по стабильному `Status`, а не по тексту ошибок или процентам.
- Цвета доступны в тёмной теме: completed=green, queued=grey, running=cyan, interrupted=amber, failed=red.

Сохраняй Settings.ShowVideoTitles и Queue.Title совместимо с прежними данными. ## Сборка и packaging

Единственный проект приложения — `src/VideoDownloader/VideoDownloader.csproj`: Windows x64, .NET 8, WPF, автономный EXE. Пользователь запускает EXE напрямую. Обязательны соседние yt-dlp, XAML, ресурсы и `collection-plugins/`; единственный EXE не заменяет весь portable ZIP.

`scripts/build.ps1 -Task Publish` создаёт `dist/native`, `dist/VideoDownloader-native.zip` и SHA-256. Параметры `-Version`, `-OutputDirectory`, `-ArchivePath`, `-ChecksumPath` позволяют main-only release job выбрать версию и имена файлов без второго упаковщика.

Пакет обязательно включает `collection-plugins/videodownloader/yt_dlp_plugins/extractor/vd_pornhub.py`; копируй только исходные `.py`, без `__pycache__`/`.pyc`. Проверка пакета должна отклонять CMD, `.ps1/.psm1`, `pwsh.exe` и launcher вместо приложения. Внешний Python пользователю не нужен.

## Тесты перед PR/merge

На Windows с .NET 8 SDK и PowerShell 7 выполни из корня:

~~~powershell
pwsh -NoProfile -File scripts/build.ps1 -Task Test
~~~

Команда собирает приложение и выполняет release-version/Russian/smoke, нативные unit/integration/security/legacy tests и реальные WPF-сценарии с изолированным профилем. Не подменяй холодное получение метаданных тестом с готовым кешем. Проверяй все пути добавления URL/TXT/InternetShortcut/подписка до Start без выбора строки, а также singleton/протокол/трей и все варианты диалога повтора.

Исполняемые проверки находятся в `tests/VideoDownloader.Tests/` и `tests/VideoDownloader.UiTests/`: `LegacyCompatibilityTests` читает фиксированные старые данные; `SubscriptionStoreTests` и `SubscriptionScannerTests` проверяют обнаружение, RSS и состояния; WPF host проверяет настоящие контролы. Не заменяй эти сценарии поиском маркеров в исходниках.

Для коллектора выполни `python tests/pornhub-collector-tests.py` с версией yt-dlp, закреплённой в Windows CI. Windows-тест адаптера дополнительно проверяет загрузку плагина настоящим упакованным `yt-dlp.exe` на офлайн-страницах. Живую проверку сайта описывай отдельно и не выдавай фикстуры за доступ к реальному каналу.

Если менялась упаковка:

~~~powershell
pwsh -NoProfile -File scripts/build.ps1 -Task Publish
~~~

Для изменений кода, тестов, скриптов и сборки единственный Windows workflow `native-windows.yml` должен быть зелёным перед merge. Smoke проверяет синтаксис скриптов разработки, XAML и обязательные файлы/контролы; функциональные проверки выполняют C#-тесты. PR только с Markdown может не запускать workflow из-за фильтра путей: перед его merge проверь ссылки, якоря, Mermaid и соответствие инструкций исходникам. После push в `main` полный workflow запускается независимо от состава изменений.

Для нетривиальных изменений:

3. PR;

## Документация

При изменении поведения синхронизируй:

- `README.md` — обзор, установка, ссылки на четыре пользовательских сценария и команды разработки;
- `docs/USER_GUIDE.md` — пошаговое скачивание видео YouTube, импорт плейлиста, подписки и необязательная RSS/Atom;
- `GUI.md` — справочник кнопок, параметров и ограничений;
- `docs/ARCHITECTURE.md` — компоненты, жизненные циклы URL/подписки/проверки RSS, отмена, хранение и восстановление;
- `AGENTS.md` — архитектурные правила и обязательные проверки;
- `RELEASING.md` — сборка и публикация, если менялся выпуск.

Документация должна описывать текущую реализацию и реальные ограничения, а не планируемые функции.

В пользовательских инструкциях используй фактические подписи контролов из XAML. Различай прямой URL плейлиста (одна задача движка, состав определяет yt-dlp) и импорт через подписку (отдельные URL материалов). Не обещай отдельную строку/историю на каждый ролик при прямом URL коллекции. Для одного YouTube-видео в примере не оставляй `list` в адресе.

RSS/Atom не является отдельным планировщиком или источником новых элементов поверх полного списка: она только дополняет отсутствующие названия для точных URL, подтверждённых обязательным обходом коллекции. В руководстве сохраняй основной URL коллекции и необязательный FeedUrl как разные поля. Cookies из UI передаются yt-dlp, но не RSS HTTP-запросу.

Диаграммы веди в Mermaid внутри Markdown с понятными подписями и ссылками на настоящие компоненты. Показывай независимость preview от скачивания, границу ручного Start, отдельные записи session/history/subscriptions и сохранение прежнего снимка при неполной проверке. Не изображай эти файлы одной общей атомарной транзакцией. После правок проверь локальные ссылки, якоря и синтаксис/отрисовку всех диаграмм; примеры URL с заменяемыми ID явно помечай как шаблоны.
