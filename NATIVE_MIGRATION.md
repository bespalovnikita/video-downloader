# Переход Video Downloader с PowerShell на C# / .NET 8

Согласован следующий переход: оставить только нативный WPF-интерфейс и одну
сборку. [Поэтапный план](docs/UI_ONLY_PLAN.md) и
[матрица проверок перед удалением второй реализации](docs/UI_ONLY_COVERAGE.md)
описывают эту работу. Первый этап добавил нативные регрессионные тесты и
фиксированные старые данные. Нативный CLI удалён; CMD и PowerShell-версия
пока сохранены до согласованного удаления старой сборки.

## Архитектура новой версии

Основное приложение работает на **C# / .NET 8** под Windows. Интерфейс остаётся **WPF** и загружает общую разметку `ui/MainWindow.xaml`. Очередь, работа с `yt-dlp`, история, кеш, отмена и трей реализованы внутри процесса `VideoDownloader.exe`.

Нативная версия **не использует `pwsh.exe`**, не открывает чёрное окно PowerShell и не требует установленного PowerShell 7. Внешними процессами остаются `yt-dlp.exe` и при необходимости FFmpeg.

Сборка для Windows x64:

~~~powershell
dotnet publish native/VideoDownloader.Native.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:EnableCompressionInSingleFile=true -o dist/native
~~~

В `dist/native` входят `VideoDownloader.exe`, `yt-dlp.exe`, XAML и иконка. Не нужно копировать туда `.ps1`, `.psm1` или `pwsh.exe`.

## Что осталось от PowerShell

В репозитории сохранены `start-gui.cmd`, `ytdl-manager-gui.ps1`, `ytdl-manager-v8.ps1` и библиотеки `lib/`. Они служат резервным вариантом, инструментом совместимости и старым CLI.

Если `start-gui.cmd` находит `VideoDownloader.exe` рядом или в `dist/`, запускает именно C#-приложение. При отсутствии EXE запускает PowerShell GUI; в таком случае нужен PowerShell 7.

В обеих версиях общий файл XAML. Поэтому добавлены одинаковые элементы: кнопки открытия папки загрузок и папки настроек, русские названия профилей. Файлы данных при этом общие. **Не запускай обе версии одновременно.**

## Соответствие возможностей

| Возможность | Реализация на C# |
| --- | --- |
| Очередь и изменение порядка | `ObservableCollection`, обработчики WPF |
| Добавление ссылок на лету | Канал задач и асинхронный пул работников |
| Несколько загрузок одновременно | Отдельные процессы `yt-dlp` и ограниченная параллельность |
| Прогресс, скорость и время | Разбор структурированного вывода `yt-dlp --progress-template` |
| Отмена и остановка | `CancellationToken`, завершение дерева процессов |
| Пауза | Приостановка/возобновление дерева процессов Windows |
| Безопасное удаление | Индивидуальная staging-папка и список `OwnedPaths` |
| Превью | Фоновый процесс метаданных, загрузка изображения, кеш на 72 часа |
| История | Совместимый журнал JSONL, диалог повторной загрузки |
| Восстановление | `session.json` версии 1 и старые `events.jsonl` |
| Трей | `NotifyIcon`, статистика `OK → Left → Err` |
| Настройки профилей | Русские подписи, прежние английские идентификаторы |
| Подписки | Ручное перечисление каналов и плейлистов через yt-dlp, необязательная RSS/Atom, входящие и очередь следующего Start |
| Протокол браузера | Регистрация `videodownloader://` для текущего пользователя |
| Передача ссылок и файлов | URL / TXT / InternetShortcut / протокол передаются в интерфейс существующего окна |

EXE всегда запускает WPF-интерфейс; отдельного нативного `--cli` больше нет.
Передача URL или файла не запускает скачивание автоматически: используется
кнопка **Start**. Второй экземпляр передаёт аргументы в уже открытое окно.

Для изолированных прогонов разработчик может задать `VD_DATA_DIRECTORY`:
приложение использует этот каталог и отдельный экземпляр для него. Обычный
запуск сохраняет прежний `%LOCALAPPDATA%\VideoDownloader`; сам путь данных
не меняется при обновлении. Startup-тест запускает настоящий EXE во временном
профиле, тест singleton — два процесса через тот же путь запуска WPF.

## Совместимость сохранённых данных

Каталог пользовательских данных:

~~~text
%LOCALAPPDATA%\VideoDownloader
~~~

Он доступен по кнопке **«📁 Открыть папку настроек»** рядом с `Register protocol` в обеих версиях.

| Данные | Путь | Совместимость |
| --- | --- | --- |
| Очередь и параметры | `session.json` | Формат версии 1, одинаковый для C# и PowerShell |
| История успешных URL | `successful-downloads.jsonl` | Прежний append-only JSONL; сохраняется время загрузки |
| Кеш превью | `preview-cache\` | SHA-256 URL, TTL 72 часа |
| Подписки и входящие | `subscriptions.json` | Отдельный формат версии 1, общий для C# и PowerShell |
| Результаты старого движка | Путь `Engine.EventsPath` из checkpoint | C# считывает финальные результаты после закрытия старого движка |

Профили хранят прежние значения `Universal`, `4K archive`, `MP4 compatibility`, `Music MP3` и `Subtitles archive`, хотя пользователь видит русские названия. Это **не требует миграции JSON** и сохраняет совместимость со старыми сессиями.

При восстановлении активная ранее загрузка становится `Interrupted`, а завершённая не запускается повторно автоматически. Если старый процесс `pwsh` всё ещё выполняет загрузки, C#-приложение блокирует начало новой сессии, чтобы не повредить историю.

Обе версии восстанавливают настройки при пустой или полностью завершённой очереди и при отказе от восстановления строк. Автосохранение и отслеживание буфера включаются после восстановления; при открытом диалоге исходный checkpoint защищён от записи. Ошибка чтения оставляет файл неизменным.

Нативные процессы загрузки yt-dlp создаются сразу в индивидуальном Windows Job Object с `KILL_ON_JOB_CLOSE`. Аварийное завершение владельца закрывает job и завершает дерево загрузчика. Явный список наследуемых pipe handles исключает наследование job другим работником. Превью и проверка подписок используют тот же механизм; открываемые через оболочку пользовательские приложения в эти jobs не входят. Обновление `yt-dlp -U` сохраняет отдельный запуск, чтобы его штатная отложенная очистка старого EXE могла завершиться после выхода обновляющего процесса.

При добавлении ссылок C# повторно проверяет очередь и исходную сессию после модального диалога. Повторный вход не создаёт дубликатов; завершившаяся или сменившаяся сессия оставляет ссылку для следующего Start. Проверка границ файлов поддерживает корни дисков и UNC. Скачивание установщика FFmpeg ограничено шестью минутами на заголовки и всё тело ответа.

Перед началом GUI/CLI проверяют необходимые FFmpeg и ffprobe. Нативный CLI возвращает ненулевой код при отсутствии зависимостей. Контейнер задаёт merge и remux, а несовпадение расширения итогового media с выбранным контейнером блокирует публикацию.

## Подписки и границы текущей реализации

Обе версии GUI используют `ui/SubscriptionsWindow.xaml`. В основной версии подписки обслуживает код C#, в резервной — модули `VideoDownloader.Subscriptions.psm1` и `VideoDownloader.SubscriptionUi.psm1`. Сканирование выполняется отдельно от фонового предпросмотра; проверка плейлиста не ограничивается первым элементом.

Подписка хранит полное название коллекции и редактируемое краткое имя `ShortName`. Первая успешная проверка заполняет пустое имя из названия канала/автора, затем из названия коллекции. Последующие проверки не переименовывают папку. Старые записи версии 1 без `ShortName` читаются с пустым значением; остальные проверки схемы сохраняются.

Новые задания из подписки сохраняют `SubscriptionId` и снимок `SubscriptionName` в общем `session.json`. При Start движок добавляет это безопасное имя папки к зафиксированному каталогу сессии: `D:\Video\123` либо `D:\Video\ГГГГ-ММ-ДД\123` при архивировании. Переименование подписки влияет на будущие добавления, а уже поставленные задания и существующие обычные URL сохраняют прежнее назначение. Отсутствующие поля старого checkpoint означают обычное задание без подпапки подписки.

Нативный координатор фиксирует фактический каталог каждого задания и использует его при публикации, отмене и сохранении `OutputRoot`. Резервный GUI передаёт снимок папок движку через `-ItemFoldersFile`; обычные и добавленные через live ingress URL без записи манифеста используют общий каталог сессии. Краткое имя допускает только один компонент пути, а проверки reparse points и владения файлами сохраняются для итогового каталога каждого задания.

Полный просмотр через установленный `yt-dlp` поддерживает HTTP/HTTPS-коллекции всех доступных ему сайтов. RSS/Atom необязательна: YouTube-лента может определяться по метаданным, адрес другой ленты можно указать вручную. Недоступная лента даёт предупреждение, но не отменяет успешное полное перечисление через `yt-dlp`. Полный список yt-dlp определяет состав подписки. RSS обогащает только совпавшие по точному URL элементы; ссылки только из ленты не добавляются во входящие. RSS не заменяет полную проверку и не служит основанием пропустить её.

Локальный ключ материала — `SubscriptionId` и точный `Url` с ordinal-сравнением. Сопоставления по media ID или неявного удаления query-параметров нет. Первый полный просмотр либо устанавливает исходный набор, либо помечает существующие материалы для добавления в очередь согласно явному выбору пользователя. Новые ссылки следующих проверок попадают во входящие. Добавление из подписки всегда ожидает следующего Start и не использует добавление в активную сессию.

Состояния `Baseline`, `New`, `Queued`, `Processed`, `AlreadyProcessed`, `Skipped` сохраняются одинаково в обеих версиях. Успех подтверждает только реальный успешный результат движка или постоянная история успешных URL. При совпадении точного URL с успешно обработанным материалом другой подписки уведомление показывается один раз, а подтверждение показа сохраняется. Если успех известен лишь из общей истории без связи с другой подпиской, устанавливается Processed без уведомления. Обнаружение, постановка в очередь и пропуск не считаются обработкой.

Предел обычного полного просмотра — 10 000 материалов, 180 секунд и 32 МиБ метаданных, предел RSS/Atom — 2 МиБ и 12 секунд. В обоих GUI публикации Pornhub перечисляет отдельный обработчик из `collection-plugins/`: до 10 000 роликов, 500 страниц и 15 минут. Он запускается явно внутри `yt-dlp.exe`, не требует внешнего Python и возвращает проверяемый манифест страниц с отдельными URL видео. История просмотров и рекомендации исключаются. Для всего архива выбери добавление существующих материалов в «Подписках», затем Start. Каждый ролик сохраняет обычную семантику очереди, истории, отмены и повтора.

Неполный, некорректный или превышающий предел ответ не меняет исходный набор, материалы и время последнего успешного просмотра. `subscriptions.json` записывается атомарно под общей межпроцессной блокировкой. Повреждённый файл сохраняется без перезаписи.

Общий обработчик допускает редиректы между `/videos/upload` и `/videos` того же профиля и использует конечный адрес для следующих страниц. Неподходящий редирект сообщает адрес назначения; переход на другой профиль, главную страницу или вход не считается полным списком публикаций.

Варианты разметки списков (`claimedUploadedVideoSection`, `moreData.videos`, `videoUList` и отдельные списки каналов) обрабатываются тем же плагином в обоих GUI. Он исключает боковые панели и рекомендации, отклоняет неоднозначные списки и сообщает структурную диагностику нераспознанной страницы. Подтверждение возраста в браузере передаётся приложению через файл Cookies; браузерная сессия не используется автоматически.

Текущая реализация охватывает ручные проверки и управление входящими. Автоматические таймеры, отдельный запуск из Планировщика Windows, автоматическая загрузка и дополнительные правила находятся в [BACKLOG.md](BACKLOG.md).

## Безопасность скачанных файлов

Каждый URL получает отдельную временную папку. Готовые файлы публикуются в папку назначения без перезаписи существующих файлов. При удалении используется только явно известный список `OwnedPaths`: одного пути из старого checkpoint недостаточно.

При совпадении имён движок выбирает свободный суффикс для всего набора media/sidecars. Например, `video.mp4` и `video.en.srt` становятся `video (2).mp4` и `video (2).en.srt`. Внутри native-процесса планирование и публикация согласованы общей блокировкой; гонка с другим процессом по-прежнему не разрешает перезапись чужого файла. Прямой вызов файлового helper без разрешения переименования отклоняет коллизии.

Проверяются границы каталога, выход через `..` и NTFS junction/symlink/reparse point. Папка назначения в режиме архивирования фиксируется на всю сессию, чтобы переход через полночь не менял место удаления и публикации.

Отмена URL согласована с публикацией результата и не должна затрагивать соседние задания. Проверки выполняются перед файловыми операциями, но они не дают абсолютной гарантии против намеренной одновременной подмены каталогов (TOCTOU). Для полной защиты от такого противника нужен Win32 API с операциями по открытым дескрипторам файлов.

При переходе между версиями сохраняются `PendingRemoval`, `CleanupError`, `CleanupPaths`, `StageDir`, `RunDir`, `OutputRoot`, `AttemptFinished` и `DeferredToNextStart`. Незавершённое удаление исключается из запуска и остаётся доступным для повторного Remove после восстановления. Обе версии понимают имена staging-папок друг друга; пути проверяются до удаления. Старый `Path` без манифеста владения не разрешает удалять файл.

События предыдущей попытки не применяются к строке `DeferredToNextStart`: повторно добавленный URL остаётся в очереди следующего запуска. Последняя корректная JSON-запись истории без LF поддерживается обоими движками; повреждённый хвост сохраняется без изменений.

Профили полностью задают один и тот же набор параметров в обоих интерфейсах. Предпросмотр ограничен 30 секундами на запрос, 12 секундами и 2 МБ на изображение; зависший процесс завершается, а работник переходит к следующему URL.

## Тестирование

Workflow `.github/workflows/native-windows.yml` выполняет на Windows:

- компиляцию C# и фактический запуск WPF-окна;
- проверку добавления/удаления URL и восстановления checkpoint;
- проверку русских профилей и новых кнопок в общем XAML;
- тесты фонового превью, кеша, зависшего metadata-процесса и тела изображения;
- проверки истории без LF, всех переходов профилей, восстановления отложенных попыток и контекста очистки;
- отмену при заблокированном NTFS-файле, сохранение ошибки и успешную повторную очистку;
- реальные локальные загрузки через `yt-dlp`, параллельность, отмену и паузу;
- проверки файловой безопасности, NTFS junction и контрольных файлов вне папки;
- сборку автономного ZIP без PowerShell.

Отдельный workflow `build-windows.yml` проверяет резервный PowerShell-интерфейс и CMD-сценарий. `tests/cross-runtime-contract-tests.ps1` проверяет обмен историей и очередью PowerShell → C# → PowerShell, очистку staging и совпадение профилей. `tests/preview-deadline-tests.ps1` проверяет таймауты процесса и тела изображения в резервной версии. Эти два теста требуют PowerShell 7.4 или новее; в изолированной проверке ядра заменяется только граница уведомлений WPF. Реальное WPF-окно отдельно проверяет native Windows CI.

## Выпуск обновлений

**Каждый успешно протестированный коммит в `main` считается релизным**. GitHub Actions выбирает версию `v2.0.N`, формирует ZIP с готовой программой и `SHA256SUMS.txt` и публикует GitHub Release.

Страница загрузок: https://github.com/bespalovnikita/video-downloader/releases/latest

Полные правила описаны в [RELEASING.md](RELEASING.md). Резервная PowerShell-версия остаётся в исходниках и не включается в архив нативного релиза.
